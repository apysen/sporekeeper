# 2026-09-08

## The project is called Sporekeeper, and the code finally says so

`phase_b_` was a milestone label that outlived its milestone. It prefixed 40 files
and all 38 class names, which meant it carried no information at all — a prefix
every type shares distinguishes nothing. It is gone.

- **Files and classes lost the prefix.** `PhaseBCombatDirector` is `CombatDirector`,
  `PhaseBProgression` is `Progression`, and so on for all 38. No collisions with
  engine types.
- **The run root is named after what it is.** `phase_b_prototype.gd` →
  `run_root.gd` (`class_name RunRoot`), `phase_b_prototype.tscn` →
  `scenes/run/run.tscn`, `phase_b_prototype_smoke.gd` → `tests/run_smoke.gd`,
  `docs/phase_b_prototype.md` → `docs/run_composition.md`. `RunRoot` is the name
  the composition doc already used for it.
- **"Elemental" became Sporekeeper** in `project.godot`, the inspector addon, and
  `docs/sporekeeper_composition_conventions.md`. It survives only as the adjective
  it always was — "elemental territory-control" — which is correct.
- **The repository moved** to `D:\GameDev\sporekeeper`.

## The run scene was a 163-node god-scene; it is now 62 and five sub-scenes

One `.tscn` held gameplay, every enemy profile, the whole side panel, the slot
cabinet, the draft panel and the pause menu. Its root declared **86** exported node
references in a single `PackedStringArray` — one for every control anywhere in the
tree — because nothing was instanced and so nothing could own anything.

This is the project's own written convention, not a new idea:
`docs/sporekeeper_composition_conventions.md` already said scenes are composition
roots and that `RunRoot` must not grow merely because it can reach most of the
game. The code had drifted from the doc; it never disagreed with it.

| | before | after |
| --- | --- | --- |
| `run.tscn` nodes | 163 | **62** |
| `run.tscn` lines | 2192 | **812** |
| `RunRoot` exported references | 86 | **51** |
| `run_root.gd` lines | 3641 | **2064** |

Six regions moved out, each owning its own presentation and reporting what
happened rather than being reached into:

- **`scenes/ui/menus/pause_menu.tscn`** — the pause panel, the settings page, the
  volume and fullscreen controls, the dev-control card. Reports `opened`, `closed`,
  `settings_toggled`, `glossary_requested`, `main_menu_requested`, `quit_requested`.
  What pausing *means* — which simulations stop — stayed on the run root, because
  that is a run rule and not a menu's business.
- **`scenes/ui/hud/slot_machine_panel.tscn`** — reels and their near-miss rewind,
  the lever, the wager notch, the odds readout, the pair-focus scaling. It drives
  `SlotMachine` directly, because it is that machine's view; what it hands back are
  only the things a spin costs the run (`spin_started`, `spin_refused`,
  `cinematic_started`, `cinematic_ended`).
- **`scenes/ui/hud/adaptation_tree.tscn`** — the two Core rows, the Evolution
  between them, and the two Branch rows, with all 20 of the `@onready` references
  that used to live on the run root.
- **`scenes/ui/drafts/choice_panel.tscn`** — a heading, four cards and a reroll, and
  deliberately *nothing* about what a card means. It is handed finished
  `{text, modulate}` entries, which is what lets one panel serve an upgrade draft, a
  relic reward and a milestone Adaptation offer.
- **`scenes/enemies/enemy_profiles.tscn`** — the authored roster. Enemy tuning is now
  one file to open instead of two hundred lines in the middle of the run scene.
- **`scenes/run/run_audio.tscn`** — the ambient theme, the three Clover voices, and
  the WAV loop-bounds repair.

A sub-scene that needs a collaborator from the parent scene is handed it once
through an explicit `setup()` the run root calls from its own `_ready`. Nothing
authors a NodePath that climbs out of its own scene.

## Enemies stay pooled structs, deliberately

The composition pattern this follows is scene-level, not entity-level. Enemies,
projectiles, pickups and traps remain `EnemyState`-style structs in pooled arrays
with spatial grids and `PerfCounters` measuring them. Turning them into a node per
entity is the usual next step in this pattern and would be wrong here: it would
throw away the optimization work `docs/performance_optimization_implementation_guide.md`
exists to protect, for a horde game that spawns them by the hundred.

## `src/core/rules/` exists at last

`docs/project_structure.md` has specified a `rules/` folder for scene-independent
game rules since it was written, and nothing had ever been put there. Pure logic
lived inside the nodes, which is a large part of why `run_root.gd` was 3641 lines
and `combat_director.gd` is 6391.

**`src/core/rules/progression/upgrade_descriptions.gd`** (540 lines) is the first
tenant: every line the interface prints about an upgrade — its two-letter slot
abbreviation, its hover, the finished numbers a rank resolves to, and what the Root
Network makes of them. `_get_upgrade_resolved_effect` alone was 188 lines reading
nine different components.

It is scene-independent but not pure, and that is the point: "resolved" means the
numbers are read from the same getters the systems use, so a hover can never drift
from what the run is actually doing. It lives outside the tree so the run root and
the Adaptation tree can both hold one without either reaching through the other.

The authored wording it formats with — `root_potency_note_template` — stayed an
Inspector export on the run root. The scene is the design surface; the rules module
formats with that template but never owns it.

This is what unblocked the Adaptation tree. Extracting that scene first would have
left it calling back into its parent for every string it draws, which is the
coupling inverted rather than removed.

## Two tooltips that were never firing

Moving code that had been sitting still turned up two handlers that were defined,
complete, and connected to nothing:

- **`_on_reward_hovered`** — draft-card tooltips. Nothing was ever connected to the
  choice buttons' hover.
- **`_on_hud_slot_hovered`** — HUD slot tooltips. `UpgradeSlots` has emitted
  `slot_hovered` all along and nobody listened.

Both are now wired: the Adaptation tree connects its five rows in its own `_ready`,
the run root connects the relic row it still owns in the tray, and the choice panel
reports `option_hovered`. `MechanicsHelp.tooltip_body` is a static shared by both
owners rather than a copy in each. **These change runtime behaviour — tooltips that
did not appear before will now appear, and want a look in-game.**

## The wording guard learned to follow sub-scenes

`run_smoke`'s rule that *every line the game prints is the wording its scene node
declares* built its list by walking `run.tscn`'s `SceneState`, and self-guarded with
`declared_texts.size() > 20` so it could never pass by finding nothing.

That guard fired during this work — correctly. Wording had not broken; the wording
had *moved*, into instanced sub-scenes the check could not see, and it refused to
keep vouching for a surface it had lost sight of. Lowering the threshold would have
left the pause menu, the slot cabinet, the draft panel and the Adaptation tree
unchecked forever. Instead the check now recurses through `get_node_instance()` into
every sub-scene, prefixing paths with the instance's own path. The companion layout
check — *nothing moves a control the scene placed by hand* — had quietly lost the
same coverage without a threshold to catch it, and follows instances too.

## Verification

`run_smoke` was captured as a baseline before any of this and re-run after every
single extraction, never batched: **353 passing checks and the same six pre-existing
failures**
(nine-patch borders, two Cane sector checks, the discharging ring, UI Scale,
Detailed/Compact), byte-identical failure set, no script errors.

`ui_alignment_probe` output is character-for-character identical to the
pre-refactor commit, including `PausePanel/NinePatchBorder intrudes 14px` — the
extracted pause menu resolves to the same nodes at the same coordinates.
`campaign_no_clover_probe`, `slot_content_probe`, `ui_text_fit_probe` and
`run_mode_probe` pass.

Two failures were confirmed **pre-existing** against a clean worktree at `aabb446`,
not caused by this work:

- **`wager_slider_probe`** — "bar is 10px where the meters are 32, wanted 16". The
  stake slider's track is drawn at a third of its intended thickness. Worth fixing.
- **`slot_symbol_probe` hangs under `--headless`**, as do the eight other probes
  that call `root.get_texture()`, `save_png()` or `Input.warp_mouse()`. They need a
  real rendered viewport. Wrap probe runs in `timeout` so a hang reads as 124.

Two bugs it caught in the Adaptation tree extraction, both worth recording because
the suite is the only reason neither shipped:

- **`%Slots` resolved to null.** The run root's `slots_label` export became
  `@onready var heading_label = %Slots`, but `Slots` was the one node in that group
  with no `unique_name_in_owner` marker — precisely *because* it had been an export
  rather than a `%` lookup. The heading write crashed on a null. Every `%` lookup in
  the extracted components is now audited against the markers actually present in
  their scenes.
- **A label's authored template followed its node into the sub-scene, and the test
  did not.** `run_smoke` re-authors wording the way it would be re-typed in the
  editor, via `prototype._authored.set_template(...)`. Once the Adaptation tree
  captured its own heading, setting the template on the run root's registry changed
  nothing and the heading printed its original wording. Each probe now names the
  `AuthoredText` that owns its label, so a label inside a sub-scene is re-authored
  through that sub-scene's registry. The same lesson as the wording guard above:
  when a node moves, the thing that vouches for it has to move with it.
