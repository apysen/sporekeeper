# 2026-09-11

Continues 2026-09-10, which ended with every probe passing, one check that nothing ran,
and two open items that were both waiting on the same missing feature. The check runs
with the suite now, and the missing feature is saving.

## The shadowed-name check was a check nobody ran

`tools/check_shadowed_names.gd` was written yesterday and verified by reintroducing a
collision, which is the right standard. What it did not have was a caller. Nothing in
the project referenced it - no runner, no suite, no line in `project_structure.md` -
so it caught collisions only on the days someone thought to type its path.

That is the weakest possible position for the one defect class `--import` cannot see.
A shadowed `get_name` parses, imports, reports no error, and fails at the call site
with *"Expected 0 argument(s)"*; it has shipped twice in this project already, and
both times the build was green. A check for it that depends on being remembered will
be as reliable as the memory of whoever last read the changelog.

### The scan became its own class

`tools/shadowed_names.gd` holds `ShadowedNames.scan()`, which returns one message per
collision - file, line and name - and an empty array when every declaration is
reachable. The `INHERITED` list and the `func`-line parsing moved with it unchanged;
the only new thing is `ROOTS`, which names `src`, `tests` and `tools` as a constant
rather than as an expression at the one call site, because there are two call sites now.

`tools/check_shadowed_names.gd` is what is left: it calls `scan`, prints, and sets an
exit code. It stays because the suite cannot serve every case - a tree that will not
boot still needs sweeping, and the scan needs nothing but the filesystem to run.

### `run_smoke` runs it first

The scan is the first thing `_run` does, before the scene is even loaded, because it
does not need the scene. It is a file scan sitting in a suite of scene checks, which
is a slight mismatch of kind, and it is there anyway for the reason that matters:
**this is the suite that actually gets run.** A collision now costs a red suite on the
next ordinary pass rather than waiting for a deliberate sweep.

It reports through `SmokeReport` like every other check, so a failure is one more
`FAIL:` line and a non-zero exit rather than a separate thing to read.

## The game saves now

`persistence/` has held one file and a doc line promising "save schema, migrations,
settings, and serialization" for as long as it has existed, and `entities/` was never
created because nothing needed it. Both were waiting on the same thing. A run now
writes itself to `user://save.dat` at every wave boundary, the title screen offers it
back, and finishing a run drops it and keeps a record of what it was.

### The state stayed where it lives

The reason `entities/` was not created yesterday still holds: `Progression`'s run state
is reached from **192 call sites in `tests/` alone**, and moving it would have rewritten
all of them. It did not have to move. The live owner of the run is still the node that
owns it; what is new is that each node can hand its state over and take it back:

```
Progression, Evolutions, Metabolism, Player, WaveDirector, TerritoryField
    capture_state() -> Dictionary
    apply_state(Dictionary)
```

`RunSnapshot` assembles those six dictionaries and **knows what is in none of them.**
That is the whole design decision. Half of what sits on these nodes is authored tuning
and scene wiring - `offer_spore_path`, the exported director references, the fifty
exported numbers that say what an Evolution *does* - and only the system itself can
tell which of its fields are the run and which are the build. A snapshot that listed
the fields would have to be edited every time one of them was added, by someone who
would have to make that judgement from outside.

So `entities/` was created with two files rather than the four folders the doc
specifies, and the doc was corrected to say why: `run/run_snapshot.gd` and
`meta/meta_record.gd`. `build/` and `territory/` describe state that has a living
owner and needs no second one.

### What a save deliberately does not hold

Nothing alive on the battlefield. No enemies, projectiles, pickups, damage numbers or
in-flight commands; no invulnerability windows or damage flashes; no pending Metabolism
injections.

That is what makes the save point a wave boundary rather than an arbitrary frame. At a
break the transient state is empty or discardable and the wave that is restored will
produce it again - so the file describes a run, not one frame of one that happened to
be serializable. It also fixes what resuming costs: the wave you were in, never more.

The field is the same argument one layer down. Eleven per-cell arrays carry history and
are saved; the claimable mask, the growth path grid, the topology, the metrics and the
Root projection are **derived and recomputed on load**, so a save cannot hold an answer
that disagrees with the cells it was computed from. A save whose grid is a different
size is refused outright rather than stretched: the arena was re-authored, there is no
honest mapping, and a run resumed onto the wrong ground would be a different run
wearing the save's progress.

### The switch had to be inverted, and that is the interesting part

The first version was `@export var save_enabled := true`, off in the suite. It was
wrong, and yesterday's changelog is why: the suite had just been caught writing the
player's `settings.cfg`.

**Forty-one test scripts load `run.tscn`**, and they advance the clock and finish runs
on purpose. Every one of them would have written over the save of whoever ran the
tests, and an opt-out would have to be remembered by every probe written from here on -
the one that forgot would be the one that cost someone their run.

So saving is off unless it is turned on, and the only thing that turns it on is
launching from the menu:

```
HomeScreen._request_launch()   RunLaunch.mark_launched_from_menu()
RunRoot._ready()               save_enabled = RunLaunch.consume_launched_from_menu()
```

A probe cannot forget to opt out of something it was never given. This is checked
directly - a probe-loaded run is driven across a wave boundary, asked to save, and the
file is confirmed to still not exist.

### Continuing

`CONTINUE  QUICK  WAVE 12` sits above the mode buttons and is hidden entirely when
there is nothing to continue, because a button that is always there and sometimes does
nothing teaches the player to distrust it. The mode and the wave come off the
snapshot's identity fields, which is what they are for: the menu describes the save
without loading a run to ask. Continuing selects **the saved run's mode**, not whichever
was last picked on that screen - a Campaign resumed as Quick would be a different game
holding the same progress.

`MetaRecord` is what survives a finished run: runs, victories, and the best wave and
Biomass in each mode, kept per mode because a wave number means a different thing in
each. Nothing in a run reads it. It unlocks nothing and grants nothing, because
inventing unlocks to justify the file would be building a feature nobody asked for; it
exists so the run that just ended is not forgotten, and so whoever builds unlocks has
somewhere to put them.

## Verification: the save system

Three new probes and one new suite module, **32 checks**, and the point of each is that
it can fail:

```
run_smoke                379 passing, 0 failures   (364 -> 379: +15, SmokePersistence)
save_store_probe         16 passing                the file: round trip, corrupt, newer build
save_resume_probe        10 passing                two real scene loads, through the file
home_continue_probe      6 passing                 the button, both ways round
check_shadowed_names     PASS
wave_cadence, campaign_density, run_mode probes    exit 0
```

`SmokePersistence` restores in memory and never touches `user://save.dat` - a suite
that saved over the player's run would be doing the exact thing this feature exists to
prevent. The three probes that must touch the file hold its bytes first and put them
back, **including putting no file back**, which is the state of a machine that has never
saved and is not reachable by writing anything.

Two checks exist only to keep the others honest. The suite module tears the restored run
back down to a fresh one and counts how many of the ten things it measured now differ -
**8 of 10** - because without that, a restore that quietly did nothing would pass every
comparison against a run that was never reset. And the end-to-end probe grows territory
before saving, so the ground check reads `4431 cells restored against 298 on a fresh
field` rather than a number a fresh run would also produce. The first draft of that
check compared 298 to 298 and passed while proving nothing.

The end-to-end probe also caught the one thing the in-memory tests could not, and it
turned out not to be a bug: a resumed run came back with 77.1 Biomass against 77.0
saved, and 91.2 health against 91.0. It had been running for the frames between its
scene readying and the probe pausing it. Demanding the number back to the decimal would
be demanding that continuing a run not continue it, so both are checked within one unit
and the reason is written next to them.

`settings.cfg` was MD5'd before and after the whole sweep and is unchanged, and no
`save.dat` is left on this machine.

## Something reads the record now

`MetaRecord` was written and accumulated correctly and nothing looked at it, which is
the same position the shadowed-name check was in this morning: correct, and therefore
worth nothing to anyone. The title screen reads it.

```
QUICK BEST WAVE 21   2 RUNS, 1 HELD
```

One line above the menu, in the same muted colour as the credit at the foot of the
screen, because it is a record and not an announcement. Two rules decide what it says,
and both are about not padding it out:

- **Hidden entirely until a first run has finished.** A row of zeroes is a worse
  greeting than no row at all, and it is the greeting every new player would get.
- **A mode nobody has finished a run in is left out**, rather than shown at wave 0. The
  line is about what happened; a mode that has not been played has not happened.

The record still grants nothing and unlocks nothing. What changed is that the run that
just ended is now visible to the person who played it, which is the whole of what it
was written to do.

## Leaving a run no longer costs you the wave

The save was written at wave boundaries and nowhere else, and quitting was documented
as abandoning the run - `_return_to_main_menu` said so in a comment. Between those two
facts, a player eight minutes into wave 12 who quit to the menu got wave 12's opening
back. The boundary is a good place to save. It is a bad place to be the *only* one.

Every way out of a run now writes:

```
wave boundary                   _on_wave_began       the clean snapshot
pause menu -> main menu         _return_to_main_menu the deliberate exit
pause menu -> quit              _quit_from_pause_menu
window close button             NOTIFICATION_WM_CLOSE_REQUEST
```

The last one matters most and is the easiest to forget: closing the window is the exit
players take without thinking of it as one. Godot delivers that notification before it
tears anything down, so the run is still whole when it arrives.

### What a mid-wave save gives back

The clock exactly, the ground exactly, the build exactly - and an empty arena for a
moment. Live enemies are still not serialized, so the wave resumes spawning from where
its schedule had reached rather than from the fight that was happening.

That is a small mercy on the way back in, and it is the honest trade for not
serializing a battlefield mid-fight. It is written next to `save_run` rather than left
for someone to discover, because the alternative - a saved run coming back with an
arena full of enemies restored from a pool, a frame at a time - is a much larger
feature bought for a much smaller reason.

## Starting a new run asks first

There is one save slot, which makes starting a new run the only irreversible thing on
the title screen. A player who meant to continue and pressed QUICK out of habit had
destroyed a run they could still have been playing, with no warning and no undo.

```
A RUN IS STILL GROWING

Your CAMPAIGN run reached wave 17 and has not ended.

Starting a new QUICK run will overwrite it. There is one save,
and it cannot be brought back.

[ START A NEW RUN ]        [ KEEP MY RUN ]
```

Three things about the wording and the wiring, each of which is the difference between
a dialog that helps and one that gets clicked through:

- **It names both runs.** The one that would be lost, with the wave it reached, and the
  one that would replace it. "Are you sure?" on its own asks the player to remember
  what they have.
- **The buttons say what they do**, rather than YES and NO. The answer that destroys
  something should be readable without the question.
- **The mode is remembered, not acted on.** Confirming starts the run that was actually
  asked for - press CAMPAIGN, keep the run, then press QUICK, and what starts is Quick.
  A dialog that launched "whichever button was pressed last" would be a worse bug than
  the one it was added to prevent.

Escape keeps the run, which is the cautious answer. Continuing is never asked to
confirm anything: it is the answer that keeps everything. And confirming drops the save
immediately rather than leaving it for the new run to write over, so a player who quits
the new run in its first seconds is not offered the old one back.

## The result panel reads the record

A run that ends now says what it was worth against every run before it:

```
A NEW BEST: WAVE 21 IN QUICK
YOUR BEST QUICK RUN REACHED WAVE 21
```

Two lines rather than one, because "wave 9" means something different when the best is
9 than when the best is 21. The previous best is read *before* this run is folded into
the record - afterwards there is no previous best to compare against, because
`record_run` has already moved it.

## The migration seam is real now

`SaveStore._migrate` discarded every older file, which is correct with one version and
no build in the wild, and was also a function that could only ever return empty. The
chain replaces it:

```
MIGRATIONS[n] : a save at version n -> the same save at version n + 1
```

A save two versions behind runs two of them in order. A version with no entry - a build
whose saves predate the chain, or a gap left by a version that was never released - is
discarded rather than half-read, and so is a step that returns something that is not a
save.

**The chain is still empty, and the seam is tested anyway.** `apply_migrations` takes
its steps as a parameter rather than reading the constant, so `save_store_probe` runs
it with a chain of its own: two steps that each stamp the save, proving they run in
order and that the result arrives at the right version carrying its contents. A seam
that has never executed is one nobody should trust on the day it is first needed -
which is the day someone's save depends on it.

### The list is discovered now

A hardcoded list is a second place to remember, and the thing nobody remembers is the
probe they just wrote. So there is no list:

- **A test is any script under `tests/` that `extends SceneTree`**, which is what makes
  a script runnable with `--script` at all. Topic modules and fixtures extend
  `RefCounted` and are loaded by the suite that uses them, so they are skipped by the
  rule rather than by an exclusion.
- **A probe needs a window if it calls `get_texture`, `save_png` or `Input.warp_mouse`.**
  Those block forever under `--headless`, and a headless run of one burns its whole
  timeout instead of reporting anything. Detected from what the probe calls, so a new
  one is classified correctly the day it is written rather than the day someone notices.

The import runs once before anything else, because a new `class_name` that has not been
imported fails every test after it with a cascade of type errors that hide whatever the
real state was. A hung probe is killed at `-TimeoutSeconds` and reported as a timeout,
rather than holding the run the way one did yesterday.

```
50 tests: 41 headless, 9 windowed
```

Forty-six of those are yesterday's; the extra three are today's save probes, picked up
without being added anywhere, which is the whole point.

### Verified by making it fail

## The restructuring, finished where finishing it means something

Asked whether the restructuring was done, the honest answer was no, and the useful
answer was a list. `docs/project_structure.md` specified six rule domains and three
existed; the home screen sat in a `nodes/menu/` the document had never heard of; and a
third of the tree the document draws is for content this game does not have.

Three different problems wearing one question. Each got a different answer.

### `rules/` has all six domains now

`combat`, `elements` and `progression` existed. `economy`, `territory` and `waves` did
not, and what belonged in them was inside the nodes:

```
rules/territory/root_stages.gd      the four bands of root development
rules/territory/nucleation.gd       r* = 2y / dg, whether a satellite survives
rules/economy/rank_costs.gd         the ladder: 20, 35, 61, 107, 188, 328, 574
rules/waves/quick_composition.gd    which enemy the next Quick pack is made of
rules/waves/wave_scaling.gd         moved from rules/combat, where it never belonged
```

Each is arithmetic over authored numbers and needs no field, no director and no scene
to be asked. `RootStages` is the one worth naming twice: the bands the interface prints
and the bands Pruning harvests in were the same numbers written once, and now they are
the same numbers written once *somewhere both can reach*.

`TerritoryField.RootStage` is `RootStages.Stage` - an alias rather than a second enum -
so every existing call site still reads the stage off the field it is asking about.

### What was deliberately left inside the nodes

**The per-cell simulation loop.** `territory_field.gd` is 3,830 lines and the largest
part of it is one loop over seven thousand cells at a fixed step, with its tuning
hoisted out by hand before the loop because a Resource property lookup per cell was
worth removing. The document calls conversion, maturity and resistance "deterministic
local operations" and it is right, but a function call per cell per step is a
measurable cost paid every frame to satisfy a folder. The rule that runs rarely moved;
the rule that runs seven thousand times a step stayed, and this paragraph is why.

That is the same judgement the pooled structs and `entities/` got on the two days
before: the layout serves the code, and where it would not, it is the layout that
bends and says so.

### The home screen moved to where the document said

```
src/core/nodes/menu/home_screen.gd  ->  src/core/nodes/ui/home_screen.gd
scenes/menu/home_screen.tscn        ->  scenes/app/home_screen.tscn
```

`nodes/ui/` is specified for "HUD, menus, drafts, objectives, and view models" and

### A third of the tree does not exist, and that is correct

Thirty-eight of the directories the document draws are absent: `scenes/pickups/`,
`data/objectives/`, `enemies/bosses/`, `models/arenas/` and the rest. There is one
arena, one boss, no pickup scenes and no authored objectives. Creating those folders
would put empty directories in the tree to satisfy a document.

So the document now says so in its own first paragraph - **"the target, not an
inventory"** - and says what is built. A folder in it is a decision about where
something goes *when it is built*, which is what makes it useful on the day it is.

One line of it was a genuine mistake rather than a plan, and is fixed: `assets/ui/` was
indented one level too deep inside `data/`, so the tree had been claiming a
`data/assets/ui/` that never existed.

### `tools/check_structure.gd`

The document cannot be checked by asking whether everything in it exists - that is
meant to fail. The direction that can be enforced is the other one, and it is the one

> **Nothing should exist that the document does not describe.**

`nodes/menu/` came to live beside the `nodes/ui/` specified for menus. The check scans
`src`, `scenes`, `data`, `tests`, `tools` and `scripts` - not `assets/`, which is
imported art organised by whoever exports it, and a document that had to list every
texture folder is a document nobody updates.
