# 2026-09-10

Continues 2026-09-09, which ended with nothing in `tests/` failing. Everything here
is structural: two retired settings deleted, eight pooled structs moved out of the
node that held them, and `tests/` finally laid out the way the doc has always said.

## Two settings that did nothing are gone

`UI_SCALE` and `HUD_DETAIL` were retired features whose vocabulary outlived them: an
enum entry, a name, a description, a choice list and a `get_choice_count` each, for
options no menu rendered and whose getters were hardcoded to `1.0` and `false`.

The blocker raised yesterday turned out not to exist. `save_settings` writes
`get_option_key(option_id)`, which is `OptionId.keys()[option_id]` — **a name, not an
index** — so dropping the two trailing options leaves every stored key in an existing
`settings.cfg` valid, and the two that no longer exist are simply never read.

Gone with them: `get_ui_scale`, `is_hud_detailed`, the `HudDetail` enum, four match
arms each, the last two entries of `default_choices`, and — the only one that was
still reachable at runtime — the `elif display_settings.is_hud_detailed()` branch in
`_update_hud` and the `status_detailed_template` export it selected.

**The guards they replaced were rewritten rather than deleted.** The property that
outlives the setting is that the HUD is drawn at 1:1 and the battlefield is never
scaled with it, so that is what is now checked, without naming an enum that no longer
exists. A half-revival cannot compile any more, which is a stronger guarantee than the
check was giving. The companion check that walked five interface-scale choices to prove
the pause panel stays centred now checks the one placement that exists, and is named
for what it measures rather than for a setting that is gone.

## `tests/` is laid out

Forty-six files sat flat against a four-folder layout the doc has specified since it
was written. They are now in it, by `git mv` so the history follows, and sorted by what
each file actually does rather than by what its name suggests:

| | files | |

| `tests/integration/` | 34 | load a scene and assert on the running game |
| `tests/performance/` | 9 | measure what something costs |

**No `visual/` folder was invented.** A visual probe loads the run scene and asserts on
it; that it also renders and saves a PNG is how it measures, not a different kind of
test. They are integration tests and they sit with the rest.

`tests/fixtures/` was **not** created. The doc specifies it, but the fixtures this
suite has - `_grow_test_ecosystem`, `_stand_on_owned_ground` and the rest - are helper
methods inside `run_smoke.gd` and cannot move until it does. An empty directory would
not survive a commit anyway, git tracking files rather than folders, so it would have
been a claim in the changelog and nothing on disk.

Twenty-one stale `## Run:` command lines inside the probes, and seven in
`docs/benchmarks/README.md`, were rewritten to the paths that now exist.

## The glossary wears the game's art now

It was the last screen drawn in the engine's default theme. `MechanicsHelp` frames its
own panel with the Kenney border and colours its headings, but its close button and
twelve letter tabs were stock grey Godot buttons - not from neglect exactly, but
because the glossary builds its buttons **in code rather than in a scene**, so there
was nothing authored for them to inherit.

They now take `button_style` / `button_hover_style` / `button_disabled_style`, the same
art every other button in the run wears, and `NinePatchButtonBorder.install_under` runs
over the finished page so the corners are sliced rather than stretched. That call is
what actually draws them: a `StyleBoxTexture` assigned straight to a Button is
stretched, corners and all, which is the whole reason that class exists.

The result was **looked at, not assumed** - the probe's own screenshot shows the tabs
and the close button carrying the same corner-bracket frame as the panel around them,
with the letters still legible at 44px wide.

`run_smoke`'s border check was the thing that made this safe to do: a Button holding a
texture style with no border is a failure there, so wiring the art without wiring the
borders could not have passed quietly. With the glossary open the run now has **30
buttons, 30 of them bordered, none textured-without-a-border and none left on the
engine's flat style.** The check's comment, which described the glossary as the reason
it skips unstyled buttons, was updated - the distinction it draws still matters, but
nothing in the run is in that state any more.

## A second render probe was waiting the wrong way

`green_wash_probe` failed once in the final windowed batch - `6036 paper on 1762381
owned pixels` where it wants zero - then passed three times in a row with every other
figure byte-identical (`green=66.7% rot=32.9% tile_px=640 max_drift=0.0000`). Only the
paper count moved, which is the signature of a readback rather than of the simulation.

It waited `await process_frame` twice before `root.get_texture().get_image()`. **Two
frames is how long it usually takes, not a guarantee that it happened.** `get_image`
returns whatever the renderer last finished, so under load - another probe on the GPU,
a busy machine - it can hand back a frame drawn before the wash was composited, and
unclaimed Paper shows through ground the simulation says is owned. It failed as the
*second* probe in a back-to-back run, which is exactly when that is most likely.

All eight readback points now `await RenderingServer.frame_post_draw`, which is the
signal that says the draw is done. Verified in isolation and in the same eight-probe
back-to-back batch that produced the failure: **all eight pass, and the paper count is
0.**

That is the second flaky probe this week to have a real cause rather than needing to be
tolerated - the first was `mechanics_help_visual_probe`'s hardcoded `* 2.0` screen
scale. Both were probes trusting an assumption about the frame they were measuring.

## `run_smoke.gd` came apart

The monolith is 8797 lines down to **1713**, as one fixture file, one ledger and
eleven topic modules. Nothing about what the suite measures changed: it is the same
358 checks, in the same order, printing the same words.

### The fixtures moved first

The 25 setup helpers at the bottom of the file - `_grow_test_ecosystem`,
`_stand_on_owned_ground`, `_find_player_frontier` and the rest - are now
`tests/fixtures/smoke_fixtures.gd`, the folder `docs/project_structure.md` has
specified since it was written and which yesterday could not be created because the
fixtures were methods on the suite.

They moved cleanly because **not one of them asserted anything**. None touched
`_failures`, none called `_check`, none awaited a frame; each takes the run it is
acting on and returns a position, a handle or nothing. That is what let all 25 become
`static` on `SmokeFixtures` in one step, with 143 call sites rewritten to name it.

A fixture that could fail a check would have made this much harder, and would have
made a failure ambiguous between the setup and the thing under test.

### The ledger is its own class

`_check` is now `SmokeReport.check`. That is not tidiness: a module has to be able to
record a result, and if it reached back to the suite by name to do it, the suite and
its modules would name each other and neither would resolve. `SmokeReport` holds the
count and nothing else, so the dependency runs one way - suite to module to ledger.

### Where the cuts were made

`_run` was one 8400-line function with **1022 top-level locals**. Splitting it on the
topic headings alone would have been guesswork, so the boundaries were computed: for
each of its 216 section starts, which locals are *read before being reassigned* after
that point. Nineteen boundaries carry nothing live but `prototype`, and every module
sits on one.

Two things had to be got right before that number meant anything.

**The suite reuses scratch names.** A naive first-declaration-to-last-use span claimed
`field` lived across 5355 lines and `launched` across 4048. They do not: those names
are scratch, reassigned in block after block, and each block writes before it reads.
Only a read-before-write test tells coupling from reuse.

**The prose counts as code if you let it.** This file is more comment than statement,
and its locals are named `grace`, `capped`, `another`, `allowed`. Scanning raw lines
for identifiers found "grace" in a sentence about a grace period and called it a read.
Stripping comments and string literals first is what took the boundary list from
uniformly-coupled to nineteen clean seams.

The locals that cross the *remaining* seams turned out to be `adaptations`, `pruning`,
`metabolism`, `waves` - all of them `prototype.X` handles, re-derived by the module in
a line rather than threaded through a signature. That is why eleven modules came out
rather than four.

### One thing actually broke, and it was worth the lesson

The suite contains **six `await`s in 8400 lines**, so ten of the eleven modules are
plain synchronous functions. Two of the six sat in the relic block and moved with it:

```gdscript
await process_frame
```

`process_frame` is the *SceneTree's own* signal, reachable by bare name only from
inside a script that extends `SceneTree`. In a `RefCounted` it is not declared in the
current scope, and the module failed to parse - which meant the class existed, the
static function did not, and the run died at the call with *"Nonexistent function
'run' in base 'GDScript'"* after 268 passing checks. The frame is now reached through
the run itself, `prototype.get_tree().process_frame`.

The failure is the reason the import step is worth running on its own: it names the
parse error and the line, where the suite only reports the call that could not be
made 200 lines away. Every later module was import-checked before it was ever run,
and the extraction script now refuses to move a block containing a bare
`process_frame`, `current_scene`, `create_timer` or `quit`.

### `CaneTargeting` - which way the sweep goes

`_densest_target_direction` was 187 lines doing two unrelated jobs. The first walks
the enemy pool, drops anything out of range or behind a wall, and builds two parallel
arrays - a direction and a distance per surviving target. The second decides an angle
from those two arrays and nothing else.

Only the first needs the node. The sweep - candidate sectors, the sorted-angle prefix
sums, the four-stage tie-breaker, both binary searches - is arithmetic over two
`Packed*Array`s, and it is now `CaneTargeting.densest_direction`. The director keeps
the gather, and keeps the `PerfCounters` timers wrapped around the call, because a
pure rule may not reach an autoload.

and that was updated rather than left an alias behind: the mode is a property of the
rule, and a second name for it in the node would be the beginning of the two drifting

The three public entry points did not move. `get_densest_target_direction` and both

The zone list stayed a plain `Array` of `[centre, radius, bonus, seconds]` rather than

### Neither of them had ever been tested

This is the part worth recording. Searching the suite for the Rampart or for either
kind of rate zone returned **one hit, in `performance_probe.gd`**, which installs the
Living Rampart relic for load and never checks what it does. Ninety lines of live
gameplay rule, reachable by two relics and a Fruit trail, with no behavioural check
anywhere.

So the move is only half the change. `smoke/bramble_and_root.gd` now ends with five
checks that did not exist before:

- a patch raises the rate under it and not beyond it
- equal patches merge into one, and overlapping unequal patches take the strongest
  rather than the sum - the rule that stops a doubled-back Fruit trail being worth
  several straight ones
- timed patches expire on their own clock while the standing Rampart outlives them
- Spore patches and Entanglement patches are two separate sets of ground, which is
  the one thing sharing an implementation could quietly break
- the Green inside a Rampart may shove again sooner than the Green outside it

The last one reports its own figures: **0.38s against 1.50s**, which is the authored
0.25 multiplier arriving intact.

Writing them after the move rather than before is worth being honest about: they were
written against code already lifted, so they prove the rule is right rather than that
it survived the lift. What proves the lift is the other 358, which are unchanged.

### The suite was writing the player's settings

Running the tests changed `user://settings.cfg` on the machine that ran them. Not a
test copy - the real file, the one the game reads on the next launch. On this machine
`DAMAGE_NUMBERS` went from the player's 1 to 0 and stayed there.

`set_choice` and `cycle_choice` both call `save_settings`, which is correct: a control
the player moves should persist. Two places in the suite drive those controls, and
neither put the file back.

**The first fix was in the wrong place.** Snapshotting the choices at the top of
`smoke/presentation.gd` and restoring them at the bottom looked right and changed
nothing - the file still came back as 0. The reason is order: `smoke/waves.gd` sets
`DAMAGE_NUMBERS` to FULL three modules earlier and never restores it, so by the time
presentation took its snapshot the player's value was already gone. It faithfully
restored the value `waves` had left.

That is the argument for putting the guard around the whole suite rather than in the
module that happens to own the checks. `run_smoke` now takes every choice once, before
the first module runs, and writes them back before the run is torn down - which also
covers whatever the next module to touch a setting turns out to be.

`damage_number_merge_probe` had this right all along, and its comment is the rule:
*"A probe that leaves the game configured differently than it found it is a probe that
changes the thing it was meant to observe."*

Proved by setting three options to distinctive values, running the suite, and reading
the file afterwards rather than assuming - the same test that caught the first attempt
failing. All three survive now, including the one that was being lost:

```
before   FRIENDLY_EFFECTS=2  TERRITORY_DETAIL=0  DAMAGE_NUMBERS=1
after    FRIENDLY_EFFECTS=2  TERRITORY_DETAIL=0  DAMAGE_NUMBERS=1
```

This machine's own `settings.cfg` was then put back to what it held before any of
today's runs touched it, and diffed to confirm.
