## The boundary was chosen by a dependency, not by taste

`EnemyState` is an inner class of `CombatDirector`, and the documented dependency
direction is that pure rules must not depend on nodes. So a rules module cannot
take an enemy — which turned out to be the right split rather than an obstacle.

**`WaveScaling` owns the numbers; the director owns the bodies they are written
onto.** It answers `get_movement_multiplier(role)`, `get_cc_resistance(role)`,
`get_action_speed_multiplier(role)`; the director does the assigning, because
enemies are pooled structs in a layout it tunes for the horde and which field a
multiplier lands on is its own business.

`_apply_campaign_role_scaling` went from 33 lines to 15, and what is left is only
assignment. The two rules that were tangled into it are now stated once each:
role resistance applies before the wave curve so a Boss stays visibly affectable,
and a grazing burst keeps its authored bite cadence while only its recovery
shortens. `_get_scaled_xp_reward` moved wholesale — it never touched a node.

Two guards were preserved rather than simplified. The original skipped interval
scaling when the multiplier was zero or negative, or when the profile opted out;
`get_action_speed_multiplier` returns exactly `1.0` in all three cases and the
director skips on `is_equal_approx(..., 1.0)`, so a division by zero is still
impossible and a no-op division is still not performed.

## The damage ledger was counting damage the player took

`damage_number_merge_probe` proves that merging ordinary hits into one number never
loses damage, by requiring `applied == shown + owed`. It was failing by exactly
`-4.0`: four points **shown that were never applied**, which is the wrong direction
for lost damage and is why it was worth reading rather than tolerating.

`spawn_player_damage_number` routes through the same `_spawn_damage_number` as every
enemy number, and that function is where the ledger is written. So Grandma's own
damage — a different subject entirely, styled apart precisely because it is not
damage the run dealt — was being added to a total that is checked against damage
applied to *enemies*. The player took 4.0 in that case, and the ledger reported it
as a discrepancy: the exact shape of the bug the ledger exists to catch, arriving
from the one source that was never a bug.

`_spawn_damage_number` now takes `is_enemy_damage`, and only the player number
passes `false`. It defaults to counting, so a new way for an enemy to take damage
is counted without anyone having to remember this.

**No runtime behaviour changes.** `debug_damage_accounting` is `false` outside the
probes, so nothing about what the game draws, or when, is different.

## The border check was asking for a border on buttons with nothing to slice

`run_smoke`'s companion check — *every run Button owns a correctly sliced
NinePatchRect border* — had been failing for a different reason, and the two faults
were unrelated despite sharing a subject.

`MechanicsHelp` builds the glossary at runtime: a close button and twelve letter
tabs. `NinePatchButtonBorder.install_under` runs once in `RunRoot._ready`, so it never
sees them — and it should not. Those thirteen buttons use the engine's own
`StyleBoxFlat`, the project having no custom theme, so a border installed on one would
find no texture, set `visible = false`, and do nothing. The check was demanding
thirteen invisible nodes.

The check now says what its own comment always said it meant. It skips a Button
drawing the engine's flat style, and in exchange it got **stronger** on the ones that
matter:

- a Button still holding a `StyleBoxTexture` is now a **failure**, not a pass — that
  is a button the border never reached, still drawing the stretch the border exists
  to prevent;
- a Button whose style is `StyleBoxEmpty` with no border is a **failure** too.
  `StyleBoxEmpty` is the fingerprint the border leaves when it captures a texture
  style, and no Button in the project is authored with one, so finding it without a
  border means the border went away and the button now draws no background at all;
- and it carries the same self-guard the wording check uses — at least ten bordered
  buttons — so a filter that stopped matching cannot pass silently.

## Two failures were the tests, not the game: both features were retired on purpose

*UI Scale scales the interface and leaves the battlefield alone* and *Detailed
reveals more on the line Compact already had* were the last two UI failures, and they
turned out not to be defects at all.

```gdscript
func get_ui_scale() -> float:
	# UI scale is intentionally fixed: the HUD is authored around the available
	# screen space and cannot be safely shrunk without harming readability.
	return 1.0

func is_hud_detailed() -> bool:
	# Compact is now the single supported HUD presentation.
	return false
```

Both say so in as many words. And neither option is reachable: `PauseMenu` builds
`setting_buttons` as five entries ending at `PLAYER_HIGHLIGHT`, while `UI_SCALE` is
option 5 and `HUD_DETAIL` option 6 — **past the end of the array, so no menu renders
either and no player can change one.** The features were removed, the menus were
trimmed to match, and only `run_smoke` was still asserting the old behaviour.

## What replaced them guards the consequence instead of the feature

Deleting the two checks would have been the easy move and the wrong one: the reason
UI Scale was ever risky is that scaling the HUD must never change how much arena the
player can see, and that constraint outlives the setting. So both now assert the
contract that is actually in force.

- **UI Scale** — that `get_ui_scale()` is 1.0, that the interface layer's scale is
  unchanged and still exactly 1.0 after a scale choice is written into the setting,
  and that the battlefield transform is untouched.
- **HUD Detail** — that `is_hud_detailed()` is false, that the status line is silent
  at rest, and that choosing Detailed leaves that line **byte-identical** rather than
  resurrecting a second presentation.

These are guards against the features coming back halfway — a scale applied to the
layer without the getter, or a second HUD design leaking into the status line — which
is the failure mode that would actually hurt.

## Two checks compared a scaled enemy against an unscaled profile

Both Cane checks assert that something out of reach took no damage, and both said so
as `is_equal_approx(get_enemy_health(id), hunter_profile.maximum_health)`.

By the time those run, the wave curve is live. A Hunter spawns with **28.64** health
where its profile says **28.0** — `maximum_health = profile.maximum_health *
_scaling.get_health_scale()` — so an *untouched* enemy compared against the profile
reads as damaged, and the check fails. Isolated, every clause passed; only in the
suite's accumulated state did the two numbers diverge.

They now measure each body against its **own** maximum via
`get_enemy_maximum_health(id)`, which already existed. The `<` clauses had the
matching flaw pointing the other way: a lightly damaged enemy at 28.2 is below its own
maximum but above the profile's, so it would have read as unharmed.

The same pattern sat in the Vine targeting check three lines of assertions long. It
was passing only because scaling happens to be neutral where it runs — a landmine
rather than a bug, and fixed while it was in view.

## The alignment probe had been measuring every panel against the wrong frame

`ui_alignment_probe` was the last failing check. Its own doc comment says it reads
each panel's frame band "off that panel's own style rather than assumed, because the
tray wears a slimmer frame than the panels do". It had stopped doing that.

`NinePatchPanelBorder._sync_style` copies the texture margins onto the border node and
then **replaces the panel's stylebox with a `StyleBoxEmpty`**. So the probe's
`get_theme_stylebox("panel") as StyleBoxTexture` returned null for every panel, and
`band` silently fell back to the assumed `FRAME_MARGIN` of 14 — including for the
RelicTray, whose real frame is 4. Its heading and slot row were being called intruders
for sitting exactly where they were authored to sit; the reported "top 5 bottom 6" is
precisely the arithmetic of a 14px band applied to a 4px frame.

Three of the five offenders were the `NinePatchBorder` nodes themselves. The border
*is* the frame, sized to the panel exactly, so measuring it against the panel's inner
rect reports the width of the band every single time.

Both are fixed at the source: the band is read off the border, which is where the real
margins now live, and the border is skipped as a child. **0 intrusions, 0 overlaps.**

**This nearly shipped a regression, and the suite would not have caught it.** The pause
menu authors its rows as templates (`"FRIENDLY EFFECTS   {value}"`); the home screen
authored a literal snapshot (`"FRIENDLY EFFECTS   FULL"`). Under `AuthoredText` that
literal becomes the template, so every home-screen row would have frozen at its
snapshot and never moved again as the player cycled the option. `run_smoke` never loads
the home screen. The five rows are now authored as templates, and were checked directly:
all five follow their value, and the snapshots were stale anyway — the authored "FULL"
is really "100%".

## `rules/combat/` gets what it was named for: a damage calculation

`docs/project_structure.md` specifies `rules/combat/` for "damage and targeting
calculations", and the wave curves that opened it are neither. **This is the first
thing there that the folder is actually named after**, and it is only possible because
`EnemyState` became a model this morning: `src/core/rules/combat/bramble_damage.gd`
takes an enemy, which a rules module could not do while the struct lived inside the
node.

`BrambleDamage` owns both halves of what a stretch of thorns does to one body: the
tick damage, and how fast that body tangles. Both are chip damage resolved per enemy
from that enemy's own Entanglement - thorn damage is never divided between the enemies
sharing a stretch of Green - and both were sitting inline in `CombatDirector`.

## Three kinds of input, told apart

The reason this is worth writing down is that the split was not obvious, and the
inputs turned out to be three different things wearing one shape:

- **Authored tuning** — eight `@export`s. Copied in once through `configure` from the
  director's `_ready`. Checked first, rather than assumed: nothing in `src/` or
  `tests/` writes any of them at runtime, so a copy cannot drift. That is what makes
  the copy safe, and it is the difference between this and `WaveScaling`, whose
  numbers are pushed in by the wave director every wave.
- **Live run state** — the Evolution-driven rate multiplier, and the local zone bonus.
  Passed per call, because they move.
- **Node-derived values** — the Root Network multiplier, which reads the territory
  field and the Root director. That one **cannot** come here at all, so the director
  resolves it and hands the finished float over. Pure rules may not touch a node, and
  this is the boundary that rule actually draws in practice.

`combat_director.gd` is 6197 → **6188**.
