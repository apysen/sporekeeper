# Sporekeeper Territory Consequence Rework
## Detailed Implementation Guide

**Status:** Revised implementation plan after codebase audit  
**Scope:** Core territory simulation, player movement, authored territory generation, hostile territory behavior, HUD readability, Adaptation interactions, telemetry, and balance validation  
**Primary goal:** Make territory ownership create meaningful moment-to-moment decisions without introducing runaway snowballing, mandatory territory builds, additional player-managed resources, or unnecessary new kill-to-territory coupling.

---

## Revision Note: Continuous-Field Correction

A codebase audit identified an important mismatch in the earlier specification.

The field does not convert discrete ownership states through a simple `Green -> Rot` spread rule. Its dominant behavior comes from diffusion and sharpening over a signed control scalar. Therefore Phase 2 now modifies those dominant terms directly and directionally.

This revision supersedes any earlier instruction that implied setting a single passive Green-to-Rot spread rate to zero would be sufficient.

# 1. Design Problem

Territory currently has a weak relationship to player decision-making.

The player can often ignore large hostile regions because:

- killing large hordes already restores substantial territory;
- losing Green usually has little immediate consequence;
- recaptured territory quickly feels equivalent to territory that was never lost;
- hostile territory percentage is primarily informational;
- raw damage frequently solves both combat and territory control at the same time;
- a high-damage build can therefore bypass much of the intended territory-management layer.

This causes the game to collapse toward a single dominant answer:

> Kill enemies faster.

The territory system should instead create additional questions during combat:

1. Can I survive the current horde?
2. Can I stop the enemy from taking an important section of the garden?
3. Can I reclaim territory that has already been lost?
4. Which region deserves my attention right now?
5. Is it worth abandoning fresh territory to protect old, established territory?

The redesign should make those questions meaningfully different.

---

# 2. Core Design Principle

Territory should be treated as infrastructure rather than score.

The intended mental model is:

> **Green is player infrastructure. Mature Green is player investment. Rot is enemy infrastructure.**

Green percentage should remain useful as a broad battlefield summary, but the important gameplay state should come from:

- where Green exists;
- how mature that Green is;
- where Rot has been allowed to remain;
- whether hostile territory has become entrenched;
- which routes and Adaptation systems depend on the threatened area.

The player should care about the shape and age of the battlefield, not only its global percentages.

---

# 3. Non-Goals

This redesign should **not** introduce the following:

- no fixed global `Rot >= X%` loss threshold;
- no global enemy damage, health, attack-speed, or movement-speed bonus based on Rot percentage;
- no universal player damage bonus based on Green percentage;
- no baseline movement penalty while standing on Rot;
- no extra enemy population generated by hostile territory;
- no new player-managed territory currency;
- no requirement that every build select a territory-focused Adaptation;
- no instant restoration of Mature Green after reclaiming lost land;
- no Canker health bar that turns territory control back into a DPS check;
- no new universal `enemy death -> territory` mechanic in the first implementation;
- no assumption that generic kills are currently the source of Green recovery.

The codebase audit shows that the generic enemy-death path currently handles combat rewards and authored Adaptation triggers, but does **not** contain a universal death-to-Green conversion. Therefore the first implementation should not add a generic death cleanse merely because the original design draft assumed one might already be required.

These restrictions are intentional. They keep the redesign focused on making the field itself meaningful rather than compensating with additional hidden stat pressure or new universal rewards for DPS builds.

# 4. Actual Territory Field Model

The territory field is **continuous**, not a three-value enum.

Each sample stores a signed control value:

```text
control ∈ [-1.0, 1.0]
```

Conceptually:

```text
strong Rot        Neutral band        strong Green
-1.0  <----------------|---------------->  +1.0
```

The current ownership threshold is:

```text
ownership_threshold = 0.18
```

So the gameplay interpretation is approximately:

```text
control < -0.18
    hostile-owned / Rot

-0.18 <= control <= +0.18
    Neutral band

control > +0.18
    player-owned / Green
```

These are **interpretations of one scalar field**, not separate stored states.

## 4.1 Why This Matters

Implementation rules should not be written as if the field performs discrete:

```text
GREEN -> NEUTRAL
ROT -> GREEN
```

state transitions.

The simulation actually evolves each cell's control continuously through terms such as:

- diffusion toward neighboring control;
- sharpening toward stronger ownership;
- natural spread;
- resistance.

Design language may continue to use Green, Neutral, and Rot because those concepts are useful to players and designers, but code-facing sections must express rules in terms of:

```text
current control
neighbor average
ownership threshold
maturity
direction of pressure
```

## 4.2 Existing Helpers

Where the codebase already provides helpers such as:

```gdscript
is_owned_at_local(...)
```

prefer those for ordinary gameplay queries rather than inventing enum-style ownership APIs.

For more nuanced systems, use the signed control value directly.

## 4.3 Threshold Hysteresis

Any mechanic that persists across frames should avoid flipping state exactly at:

```text
±ownership_threshold
```

because the field naturally oscillates near boundaries.

Use hysteresis where a mechanic has memory.

Example:

```text
consider definitely Rot when:
    control <= -0.18

remain in Rot-conversion-resistant mode until:
    control >= -0.10
```

Exact release values should be tuned, but the principle is important:

> entering a state and leaving that state should not always use the same scalar threshold.

This applies to:

- Phase 2 Rot-conversion resistance;
- Canker candidate qualification;
- any future Mature/owned gating that persists across multiple simulation steps.

## 4.4 Design Vocabulary

Throughout this document:

```text
"Green"
    means sufficiently positive control

"Rot"
    means sufficiently negative control

"Neutral"
    means control inside the neutral threshold band

"Fresh Green"
    means positive/player-owned control with low maturity

"Mature Green"
    means positive/player-owned control with high maturity
```

These names are conceptual layers over the continuous field.

# 5. Starting Territory

The player already starts with partially Mature territory.

The implementation task is **not** to create missing starting maturity. It is to replace the current control-derived player maturity ramp with an explicit starting-home rule, and to decide separately whether hostile starting territory should receive any maturity at all.

## 5.1 Current Codebase State

`reset_field()` first clears maturity:

```gdscript
_maturity.fill(0.0)
```

but the inline layout loop later seeds maturity for sufficiently owned cells:

```gdscript
_control[index] = control
if absf(control) > tuning.ownership_threshold:
    _maturity[index] = clampf(
        (absf(control) - 0.30) * 0.95,
        0.04,
        0.78
    )
```

With the current:

```text
mature_threshold = 0.66
```

the strongest part of the starting Green island can already begin above the Mature threshold.

The previous version of this guide incorrectly described the starting island as having no maturity.

## 5.2 Revised Player-Side Requirement

The desired player-facing rule is:

> The starting foothold is established home territory.

That means the positive/player-owned branch should use a **flat assignment**, not the existing control-derived ramp.

Recommended implementation:

```gdscript
_control[index] = control

if control > tuning.ownership_threshold:
    _maturity[index] = STARTING_GREEN_MATURITY
elif control < -tuning.ownership_threshold:
    _maturity[index] = STARTING_ROT_MATURITY
```

Recommended prototype:

```text
STARTING_GREEN_MATURITY = 1.0
STARTING_ROT_MATURITY = 0.0
```

This is intentionally different from merely raising the old clamp ceiling from `0.78` to `1.0`.

Why:

```gdscript
(absf(control) - 0.30) * 0.95
```

still produces low maturity near the player's starting rim because the starting control field itself falls toward the ownership threshold.

If that formula is retained, the center of the foothold can read as Mature while the rim still reads as Fresh.

That undermines the intended message:

> This whole starting foothold is home.

Therefore Phase 1 should replace the player-side starting maturity formula with a flat starting assignment for owned Green cells.

## 5.3 No Additional Layout Pass Required

The required write already exists inline inside `reset_field()`'s per-cell layout loop.

Do not add:

- a second full-field scan;
- a second starting-island representation;
- a separate starting-island helper solely for maturity seeding.

Modify the existing maturity assignment in place.

## 5.4 Important Hostile-Side Decision

The current seeding rule uses:

```gdscript
absf(control)
```

which means sufficiently strong starting Rot also receives maturity.

Because maturity contributes to `maturity_resistance_bonus`, the initial hostile mass can begin hardened against player conversion before the new Phase 2 Rot-resistance mechanic is even added.

That should now be an explicit design choice rather than an accidental consequence of symmetric initialization.

### Recommended First Prototype

```text
Starting Green:
    maturity = 1.0

Starting Rot:
    maturity = 0.0
```

This gives the player a clearly established home region while preventing accidental stacking of:

```text
starting hostile maturity resistance
× directional Rot-conversion resistance
```

If the opening hostile mass later proves too easy to reclaim, hostile starting maturity can be reintroduced deliberately as its own tuning lever.

## 5.5 Canonical Starting Invariant

Recommended first prototype:

```text
Starting player-owned Green:
    positive control above ownership threshold
    maturity = 1.0

Starting hostile Rot:
    negative control below negative ownership threshold
    maturity = 0.0

Starting Neutral band:
    maturity = 0.0

Green claimed after initialization:
    maturity = 0.0 unless an authored effect overrides it
```

The starting maturity rule is therefore about **authored initial state**, not a generic relationship between control magnitude and maturity.

# 6. Fresh Green and Mature Green

## 6.1 New Green Starts Fresh

Any newly created Green should initialize with low maturity.

Default:

```text
new_green_maturity = 0.0
```

This includes Green created by:

- Spore;
- Bloom;
- Fruit;
- passive reclamation;
- relic effects;
- kill-triggered Adaptation mechanics;
- support effects;
- recapturing previously Rot territory.

Exceptions should be rare and explicit.

A relic or Evolution that creates partially mature territory may override this rule, but this must be considered a meaningful special effect.

---

# 7. Maturity Growth

Green matures while it remains owned and uncontested.

The existing maturity system should remain the source of truth where possible.

Recommended conceptual function:

```gdscript
if owner == GREEN:
    maturity += maturation_rate * delta
    maturity = min(maturity, 1.0)
```

Maturation may continue to be affected by:

- Root upgrades;
- relics;
- Evolution effects;
- local support systems;
- campaign modifiers.

The baseline rate should be slow enough that losing a several-wave-old region feels meaningfully different from losing territory created five seconds ago.

---

# 8. Sticky Territory Loss

The most important consequence of losing land is that **reclaiming ownership does not restore the lost investment**.

Example:

Before enemy breakthrough:

```text
Green: 68%
Mature Green: 52%
```

After the player is pushed back:

```text
Green: 34%
Mature Green: 21%
```

After a strong Spore/Fruit/Bloom recovery:

```text
Green: 66%
Mature Green: 24%
```

The bar says the player has reclaimed the land.

The maturity state says the garden is still fragile.

This creates a natural recovery rhythm:

```text
Clear
→ Reclaim
→ Stabilize
→ Mature
→ Defend
```

instead of:

```text
Kill
→ Repaint
→ Fully recovered
```

---

# 9. Mature Green Movement Bonus

Mature Green should provide a modest universal movement advantage.

This is the primary universal gameplay benefit of established territory in the first prototype.

## 9.1 Design Goal

The player should gradually develop preferred movement routes across established Green.

Losing those routes should be felt directly through movement without ever making Grandma slower than her normal baseline.

## 9.2 Required Speed-Modifier Refactor

The current player speed interface exposes a single global multiplier slot through `player.set_speed_multiplier(...)`, while relic logic already writes to that same slot.

Territory must **not** write into the same single value every frame, because doing so would overwrite relic-derived speed effects.

Before implementing the terrain bonus, refactor movement speed into composed factors.

Recommended minimal structure:

```gdscript
var _relic_speed_multiplier := 1.0
var _territory_speed_multiplier := 1.0
var _other_speed_multiplier := 1.0

func get_effective_speed_multiplier() -> float:
    return (
        _relic_speed_multiplier
        * _territory_speed_multiplier
        * _other_speed_multiplier
    )
```

Expose specific setters where practical:

```gdscript
func set_relic_speed_multiplier(value: float) -> void:
    _relic_speed_multiplier = value

func set_territory_speed_multiplier(value: float) -> void:
    _territory_speed_multiplier = value
```

Do not build a large generic stat framework solely for this feature unless the existing architecture already needs one.

The important invariant is:

```text
effective movement
    = base movement
    × relic modifier
    × territory modifier
    × any other independent modifiers
```

## 9.3 Continuous-Field Territory Rule

The field is continuous, so movement should not depend on a fictional enum ownership API.

The existing helper:

```gdscript
is_owned_at_local(...)
```

is only a nearest-cell threshold check:

```text
_control[index] > ownership_threshold
```

and does not provide smoothing or hysteresis.

Likewise, the existing maturity query point-samples one cell.

Therefore the movement bonus should **not** use a single-cell ownership and maturity sample.

## 9.4 Required Local Sampling

Use a small local footprint around Grandma and compute a stable player-side average.

Recommended first implementation:

- sample the center plus 4 or 8 nearby offsets around Grandma;
- use a radius approximately comparable to a fraction of the player's collision/body footprint;
- average only inexpensive TerritoryField samples;
- compute both local positive ownership confidence and local maturity from the same sample set.

Conceptual form:

```gdscript
func sample_local_green_quality(world_position: Vector2) -> LocalGreenQuality:
    var control_sum := 0.0
    var maturity_sum := 0.0
    var green_weight_sum := 0.0

    for offset in TERRITORY_MOVE_SAMPLE_OFFSETS:
        var p := world_position + offset
        var control := territory_field.get_control_at_local(p)

        control_sum += control

        if control > tuning.ownership_threshold:
            var green_weight := 1.0
            maturity_sum += territory_field.get_maturity_at_local(p) * green_weight
            green_weight_sum += green_weight

    return LocalGreenQuality.new(
        control_sum / TERRITORY_MOVE_SAMPLE_OFFSETS.size(),
        maturity_sum / maxf(green_weight_sum, 1.0)
    )
```

The exact API names should match the existing field.

The important behavior is:

> Movement reads a tiny local patch, not one nearest field cell.

## 9.5 Movement-Side Thresholding

The local average should be considered player-owned only when it is comfortably positive.

Recommended prototype:

```text
enter Mature-Green movement eligibility:
    local_control_average >= +0.18

release eligibility:
    local_control_average <= +0.10
```

This movement-side hysteresis may be implemented with a tiny player-level boolean state because there is only one Grandma, avoiding any need for per-cell hysteresis state.

This is preferable to modifying the TerritoryField simulation for movement smoothing.

## 9.6 Tuning

Recommended first-pass tuning:

```text
maximum_mature_green_speed_bonus = 10%
```

Example interpolation:

| Local Mature Quality | Movement Bonus |
|---:|---:|
| 0.00 | 0% |
| 0.25 | ~2% |
| 0.50 | ~5% |
| 0.75 | ~8% |
| 1.00 | 10% |

Use smooth interpolation rather than discrete tiers.

Conceptual:

```gdscript
if not _territory_move_bonus_active:
    return 1.0

return 1.0 + lerp(
    0.0,
    MAX_MATURE_GREEN_SPEED_BONUS,
    local_green_quality.average_maturity
)
```

## 9.7 Important Restriction

Do **not** apply a Rot slow in the initial implementation.

Desired behavior:

```text
Rot / Neutral / unstable boundary:
    100% base movement

Fresh owned Green:
    approximately 100% base movement

Mature owned Green:
    up to approximately 110% base movement
```

Losing territory removes a home-field advantage.

It does not reduce the player's baseline capacity to recover.

# 10. Do Not Add a Universal Death Cleanse Yet

The initial implementation should **not** add a generic enemy-death territory effect.

## 10.1 Current Codebase Reality

The generic enemy death path currently handles systems such as:

- XP;
- Spore-related authored effects;
- eruptions;
- volatile behavior;
- other explicit combat/Adaptation triggers.

It does not currently contain a universal:

```text
enemy dies -> Green
```

or:

```text
enemy dies -> Rot becomes Neutral
```

rule.

Therefore adding a generic death cleanse would create a new coupling between raw DPS and territory control that the redesign is specifically trying to reduce.

## 10.2 Initial Rule

For the first territory-consequence prototype:

```text
Generic enemy death:
    no universal territory conversion
```

Only authored Adaptation, relic, Evolution, or other explicit mechanics may alter territory because of a kill.

## 10.3 Future Option

A weak universal:

```text
Rot -> Neutral
```

death cleanse may be reconsidered only if playtesting shows that non-territory builds lack a viable comeback floor **after** passive Neutral reclamation and authored systems have been tuned.

It should not be added preemptively.

# 11. Audit Authored Kill-to-Green Effects

The player's current feeling that killing massive hordes restores too much territory appears to come from **authored Adaptation and relic effects**, not from a generic death-to-territory rule.

These effects should be measured before they are nerfed.

## 11.1 Preserve Identity First

Spore and other territory-oriented systems should still be allowed to turn combat success into dramatic recolonization.

The goal is not:

> Killing should never create Green.

The goal is:

> Raw DPS should not accidentally replace territory specialization, and authored effects should not erase the cost of losing established territory too cheaply.

## 11.2 Required Source Instrumentation

Every meaningful Green-creation path should log at minimum:

```text
source
trigger_count
neutral_to_green_area
rot_to_green_area
fresh_green_created
maturity_created
```

Suggested source buckets:

```text
spore
bloom
fruit
root
bramble
thistle
vine
seedpod
pruning
plant_relic
adaptation_relic
evolution
passive_spread
other
```

The exact implementation may use IDs rather than strings.

## 11.3 Distinguish Neutral From Rot Conversion

This distinction is critical.

```text
Neutral -> Green
```

is expansion into available soil.

```text
Rot -> Green
```

simultaneously removes enemy control and establishes player control.

Those are not equivalent strategic outputs.

Telemetry and later tuning should therefore track them separately.

## 11.4 Tuning Order

Do not broadly reduce territory output at the same time as making passive Green spread asymmetric.

First:

1. implement `Green -> Neutral` passive reclamation;
2. prevent or nearly prevent passive `Green -> Rot` reclamation;
3. measure authored territory output in real runs;
4. identify which systems are actually erasing territorial setbacks;
5. tune only those systems that remain excessive.

This preserves Adaptation identity and avoids overcorrecting before the new field rules are understood.

# 12. Directional Resistance to Rot Conversion

This is one of the highest-leverage changes in the redesign, but it must be implemented against the **actual continuous field equation**.

The territory step changes control through **four** relevant channels:

1. pressure advection;
2. diffusion;
3. sharpening;
4. natural spread.

All four matter when deciding whether established Rot can be passively converted.

## 12.1 Current Pressure-Advection Stage

Before diffusion and sharpening, the field may first transport control along stored pressure:

```gdscript
var transported := control

if pressure_length_squared > 0.0 and step_max_pressure_cells > 0.0:
    ...
    transported = lerpf(
        control,
        source_control,
        clampf(advection_weight, 0.0, 0.92)
    )
```

Representative pressure behavior includes:

```text
pressure_advection ≈ 0.78
maximum per-step lerp weight ≈ 0.92
pressure_damping ≈ 0.56
```

Pressure can therefore move a cell a large distance through control space before the later diffusion/sharpening gate evaluates.

This is important because Bloom and other authored pressure-producing effects can push the frontier for several simulation steps after the initial stamp.

## 12.2 Current Post-Advection Terms

After pressure advection produces `transported`, the step includes terms of the form:

```gdscript
var diffusion := (
    neighbor_average - transported
) * step_diffusion_rate * _fixed_delta / resistance

var sharpening := (
    transported
    * (1.0 - transported * transported)
    * step_sharpening_rate
    * _fixed_delta
)

var spread := 0.0
# spread is gated by natural_spread_rate
```

Representative rates include:

```text
natural_spread_rate ≈ 0.16
diffusion_rate ≈ 1.45
```

Diffusion is substantially larger than the explicit natural-spread term, and pressure advection can already alter the cell before diffusion is computed.

Therefore setting one Green-to-Rot spread rate to zero is not enough.

## 12.3 Critical Variable Choice: Gate on Pre-Advection `control`

The Rot-conversion gate should key off the cell's **pre-advection control**, not `transported`.

Canonical decision:

```text
Was this cell established Rot before pressure advection began this step?
```

Use:

```gdscript
control
```

for that classification.

Do **not** use:

```gdscript
transported
```

as the primary "is this Rot?" gate.

Why:

A cell may begin as:

```text
control = -0.50
```

and pressure advection may move it to:

```text
transported = -0.05
```

before diffusion and sharpening execute.

If the gate reads `transported`, it concludes:

> This is no longer confidently Rot.

and the later terms can finish conversion almost unhindered.

That would let pressure advection silently bypass the core Phase 2 resistance.

## 12.4 Design Decision: Generic Pressure Does Not Bypass Rot Resistance

The recommended rule is:

> Pressure advection is a physics channel, not an automatic authored reclamation bypass.

Therefore any relic, Adaptation, or generic system that happens to add pressure should **not** receive a hidden Rot-reclamation buff merely because it changes `transported`.

If Bloom or another Adaptation is intended to reclaim entrenched Rot efficiently, that power should come from its explicit authored territory stamp or another explicit mechanic.

This keeps reclamation power legible and attributable.

## 12.5 Capture Pre-Advection Rot State

At the start of the cell step, derive a stable Rot-resistance factor from `control`.

Conceptual:

```gdscript
var pre_advection_control := control

var rot_conversion_factor := get_rot_conversion_factor(
    pre_advection_control
)
```

The helper name above is **design pseudocode only**. Production code should compute this factor inline inside the hot loop as specified in §37.2.

A smooth factor is preferred over adding persistent state to every cell.

Example:

```text
control <= -0.18:
    full Rot-conversion resistance

-0.18 < control < -0.10:
    resistance smoothly fades out

control >= -0.10:
    no Rot-conversion resistance
```

This supplies hysteresis-like stability through a continuous fade band without requiring another per-cell boolean array.

## 12.6 Pressure Advection Must Respect the Same Directional Resistance

If a pre-advection Rot cell is being advected toward more positive control, damp that positive advection.

Conceptual:

```gdscript
var transported := control

if pressure_is_active:
    var raw_transported := lerpf(
        control,
        source_control,
        clampf(advection_weight, 0.0, 0.92)
    )

    var advection_delta := raw_transported - control

    if rot_conversion_factor > 0.0 and advection_delta > 0.0:
        advection_delta *= lerpf(
            1.0,
            ROT_CONVERSION_ADVECTION_MULTIPLIER,
            rot_conversion_factor
        )

    transported = control + advection_delta
```

Recommended first prototype:

```text
ROT_CONVERSION_ADVECTION_MULTIPLIER = 0.15 to 0.30
```

Do not damp negative advection from hostile pressure into Green through this rule.

The resistance is one-way.

## 12.7 Directional Diffusion Rule

Compute diffusion from the post-advection `transported` value as the simulation already does, but key Rot resistance on the **pre-advection** cell state.

Conceptual:

```gdscript
var diffusion_delta := (
    neighbor_average - transported
) * step_diffusion_rate * _fixed_delta / resistance

var positive_diffusion_pressure := diffusion_delta > 0.0

if rot_conversion_factor > 0.0 and positive_diffusion_pressure:
    diffusion_delta *= lerpf(
        1.0,
        ROT_CONVERSION_DIFFUSION_MULTIPLIER,
        rot_conversion_factor
    )
```

Recommended first prototype:

```text
ROT_CONVERSION_DIFFUSION_MULTIPLIER = 0.10 to 0.25
```

Do not begin at exactly zero unless profiling/playtesting shows even heavily damped Rot still disappears too quickly.

## 12.8 Gate Sharpening in the Same Direction

Sharpening can otherwise finish a conversion that advection and diffusion already moved close to Neutral.

Compute sharpening as usual from `transported`, but apply the Rot gate based on `pre_advection_control`.

Conceptual:

```gdscript
var sharpening_delta := calculate_sharpening(transported)

if rot_conversion_factor > 0.0 and sharpening_delta > 0.0:
    sharpening_delta *= lerpf(
        1.0,
        ROT_CONVERSION_SHARPENING_MULTIPLIER,
        rot_conversion_factor
    )
```

Recommended first prototype:

```text
ROT_CONVERSION_SHARPENING_MULTIPLIER = 0.0 to 0.25
```

The exact value should be tuned after advection and diffusion are already correctly damped.

## 12.9 Natural Spread Is Also Directionally Gated

The explicit natural-spread contribution should use the same pre-advection Rot factor.

When an established Rot cell receives a positive natural-spread contribution:

```text
positive natural spread:
    disabled or heavily damped
```

When Green receives hostile/negative spread pressure:

```text
negative natural spread:
    unchanged
```

Recommended prototype:

```text
ROT_CONVERSION_NATURAL_SPREAD_MULTIPLIER = 0.0
```

This term is no longer mistaken for the whole mechanic. It is simply one of four gated contributions.

## 12.10 Existing Maturity Resistance Remains Separate

The field already divides diffusion by a resistance term influenced by maturity.

Do not conflate that with the new directional Rot-conversion rule.

Conceptually:

```text
maturity resistance:
    existing field-strength mechanic

Rot conversion resistance:
    one-way protection against passive positive conversion of already-hostile cells
```

The two may multiply in places where hostile maturity is deliberately allowed, which is why the starting-Rot maturity rule in §5 must be decided intentionally.

## 12.11 Preserve Full Rot Pressure Into Green

The inverse case remains unchanged.

If a player-owned or positive cell is being pushed in the negative direction by:

- hostile pressure advection;
- negative diffusion;
- negative spread;
- existing sharpening behavior;

the new Rot-conversion resistance should not damp that attack.

The target asymmetry is:

```text
Green expansion through Neutral:
    normal

generic positive pressure converting established Rot:
    strongly resisted

Rot attacking Green:
    unchanged
```

not:

```text
all territorial change becomes slower
```

## 12.12 Neutral Remains Available Soil

Do not apply full Rot-conversion resistance to every slightly negative value.

A cell such as:

```text
control = -0.03
```

is inside the conceptual Neutral band and should remain easy to claim.

The resistance factor should derive from meaningful pre-advection hostile control, beginning around the negative ownership threshold and fading out before the center of the Neutral band.

## 12.13 Authored Stamps Already Bypass Step Resistance

No new authored-bypass flag is required.

Authored territory stamps already travel through the `_commands` queue and are applied outside the per-cell simulation step. They write control directly and therefore do not pass through the Phase 2:

- pressure-advection resistance;
- diffusion resistance;
- sharpening gate;
- natural-spread gate.

This is the structural behavior the design wants.

Therefore:

```text
generic field evolution:
    respects Rot-conversion resistance

authored direct territory stamp:
    already bypasses Rot-conversion resistance
```

Do not add:

```text
bypass_rot_resistance = true
```

or equivalent plumbing unless a future authored effect is moved into the per-cell step itself.

The important design rule remains:

> Reclamation bypass should come from explicit authored control writes, not from generic pressure physics.

This also means Bloom's explicit mass/territory stamp can retain strong hostile-soil reclamation while Bloom-generated pressure advection still respects the passive Rot-resistance rules.


## 12.14 Required Debug Trace

The Phase 2 debug trace must expose **both pre- and post-advection state**.

For a sampled cell, show:

```text
control_before_advection
source_control
pressure_vector / pressure_magnitude
advection_weight
transported_after_advection
raw_advection_delta
advection_delta_after_rot_resistance

neighbor_average

raw_diffusion_delta
diffusion_delta_after_rot_resistance

raw_sharpening_delta
sharpening_delta_after_rot_resistance

raw_natural_spread_delta
natural_spread_delta_after_rot_resistance

maturity_resistance
rot_conversion_factor
```

Without `control` versus `transported`, advection-driven conversions will be misdiagnosed as diffusion/sharpening problems and the wrong multiplier will be tuned.

## 12.15 Phase 2 Success Criterion

The test is:

> Can a substantial Rot patch bordered by ordinary Green and exposed to generic pressure remain hostile long enough that the player needs an explicit reclamation mechanic or deliberate territorial intervention?

At the same time:

> Does Rot continue to attack Green at approximately the pre-rework rate?

And specifically:

> Does Bloom only gain exceptional Rot-reclamation strength from its authored territory effect, rather than from pressure advection accidentally bypassing the resistance?

All three conditions should hold before Phase 2 is considered complete.

# 13. Hostile Territory Persistence

Rot needs to become dangerous because it is allowed to remain, not because a global Rot percentage crosses an arbitrary threshold.

The system should detect **local persistent hostile control**.

This creates a spatial objective.

# 14. Cankers

A **Canker** is an entrenched hostile territory structure.

It represents enemies successfully turning long-held Rot into infrastructure.

Cankers are intentionally a **later implementation phase**.

The first prototype should determine how much consequence can be created through:

- Mature Green value;
- movement infrastructure;
- asymmetric Neutral/Rot reclamation;
- authored territory-output tuning;
- Root recovery changes.

Only after those systems are proven should Cankers be added as escalation for territory the player continues to ignore.

## 14.1 Naming Rule

The codebase already uses `BLIGHTED` as an elite modifier in the combat director and campaign content.

Do not reuse "blight" terminology for this territory structure.

Recommended implementation naming:

```text
Canker
CankerDirector
CankerCandidate
CankerNode
canker_hold_time
canker_rot_ratio
canker_spawn_redirect
```

Recommended player-facing warning:

```text
CANKER FORMING
```

This keeps the territory system semantically distinct from the existing BLIGHTED elite modifier.

# 15. Canker Eligibility

A local region becomes eligible for Canker incubation if enough of that region has remained Rot for long enough.

Recommended prototype values:

```text
canker_sample_radius = 110 px
canker_activation_rot_ratio = 0.65
canker_cancel_rot_ratio = 0.50
canker_hold_time = 10.0 s
canker_warning_time = 2.5 s
max_active_canker_knots = 2
```

These numbers are starting points only.

## 15.1 Hysteresis

Use separate activation and cancellation thresholds.

Example:

```text
Start progressing toward Canker:
    local Rot >= 65%

Cancel progression:
    local Rot < 50%
```

Do not use the same exact threshold for activation and cancellation.

This prevents the state from flickering when territory fluctuates near one boundary.

---

# 16. Canker Incubation State Machine

Recommended state machine:

```text
INACTIVE
    ↓ local Rot >= activation threshold
ACCUMULATING
    ↓ held for required duration
WARNING
    ↓ warning duration completes
ACTIVE
```

Failure paths:

```text
ACCUMULATING
    ↓ local Rot < cancel threshold
INACTIVE

WARNING
    ↓ local Rot < cancel threshold
INACTIVE
```

Conceptual pseudocode:

```gdscript
match state:
    INACTIVE:
        if local_rot_ratio >= activation_ratio:
            state = ACCUMULATING
            hold_timer = 0.0

    ACCUMULATING:
        if local_rot_ratio < cancel_ratio:
            reset_canker_candidate()
        else:
            hold_timer += delta
            if hold_timer >= required_hold_time:
                state = WARNING
                warning_timer = warning_duration
                begin_warning_fx()

    WARNING:
        if local_rot_ratio < cancel_ratio:
            cancel_warning()
            reset_canker_candidate()
        else:
            warning_timer -= delta
            if warning_timer <= 0.0:
                spawn_canker_knot()
```

---

# 17. Canker Candidate Placement

Do not evaluate every field cell as a full Canker candidate every frame.

Use a lower-frequency spatial pass.

Recommended:

```text
canker_evaluation_frequency = 2 to 4 Hz
```

Candidate centers may come from:

- territory chunks;
- coarse world grid cells;
- hostile connected-region centroids;
- existing territory partition data.

Selection should prioritize regions that:

1. have high local Rot ratio;
2. have persisted longest;
3. are not too close to an existing Canker;
4. are not too close to Grandma;
5. are not outside valid play space.

Avoid spawning multiple overlapping candidates inside the same hostile blob.

---

# 18. Canker Function

A Canker changes **spawn topology**, not spawn quantity.

This is a critical rule.

## 18.1 What It Does

A small fraction of ordinary spawn requests that would have entered from the outer perimeter may instead originate near an active Canker.

The same enemy budget is used.

Example:

```text
Wave intends to spawn 100 enemies.

Without Canker:
    100 perimeter spawns.

With Canker:
    ~85 perimeter spawns.
    ~15 redirected through Canker.
```

Total remains:

```text
100
```

## 18.2 First-Pass Spawn Redirection

Recommended:

```text
canker_spawn_redirect_chance_per_knot = 0.15
```

With two Knots, do not blindly stack this to 30% without a cap.

Use:

```text
maximum_total_canker_redirect_ratio = 0.25
```

or similar.

The purpose is to create an interior frontline, not to make perimeter spawning irrelevant.

---

# 19. Canker Spawn Restrictions

Cankers should initially be eligible only for ordinary reinforcement groups.

Do not redirect:

- bosses;
- major elites;
- Colony Cores;
- scripted wave events;
- enemies whose design requires edge telegraphing;
- any encounter whose spawn location is deliberately authored.

Recommended constraints:

```text
minimum_spawn_distance_from_player = large safety radius
minimum_spawn_distance_from_knot = small local offset
maximum_spawn_distance_from_knot = moderate local radius
```

If a valid interior spawn cannot be found:

```text
fallback → original perimeter spawn
```

Never stall or drop the spawn request.

---

# 20. Destroying a Canker

Cankers should **not have HP**.

The player defeats them by reclaiming the surrounding territory.

Recommended first pass:

```text
canker_destroy_rot_ratio = 0.35
canker_destroy_hold_time = 1.0 s
```

Example rule:

> If local Rot around the Knot falls below 35% and remains there for one second, the Knot withers.

On destruction:

- play strong visual wither effect;
- retract hostile roots or veins;
- play clear sound;
- stop future spawn redirection immediately;
- optionally convert the immediate Knot center to Neutral;
- start a local establishment cooldown.

Recommended:

```text
canker_reestablish_cooldown = 8.0 s
```

This gives the player time to capitalize on winning the territorial fight.

---

# 21. No Direct Damage Solution

Damage should not directly destroy the Knot.

Avoid:

```text
knot_hp -= weapon_damage
```

Damage can still help indirectly by killing enemies and opening space for reclaim effects.

This preserves the core message:

> This problem exists because the enemy owns the ground. Take the ground back.

---

# 22. Canker Visual Telegraphing

The player must understand a Canker before reading a tooltip.

## 22.1 Fresh Rot

Use the current Rot presentation.

## 22.2 Entrenching Rot

As the hold timer rises:

- dark veins become more visible;
- tendrils converge toward the future Knot center;
- local pulse frequency gradually increases;
- color saturation or density subtly deepens.

## 22.3 Warning State

During the final warning:

- obvious local pulsing;
- roots visibly draw inward;
- a short local warning appears;
- audio cue becomes noticeable but not alarm-spammy.

Suggested text:

```text
ROT TAKING ROOT
```

This warning should be localized near the region rather than presented as a full-screen global catastrophe.

## 22.4 Active Knot

Once established:

- clear rooted hostile structure;
- obvious link to nearby Rot;
- distinct silhouette visible through combat clutter;
- periodic pulse when it redirects a spawn;
- visual language consistent with the watercolor botanical field-guide style.

# 23. Mature Green Visual Language

The player must be able to distinguish reclaimed Green from established Green without staring at the HUD.

## 23.1 Fresh Green

Suggested qualities:

- lighter watercolor wash;
- slightly thinner pigmentation;
- sparse detail;
- fewer visible roots or botanical marks.

## 23.2 Mature Green

Suggested qualities:

- deeper pigment;
- denser watercolor texture;
- subtle visible root hairs or veins;
- richer botanical detail;
- slow ambient growth animation if performance permits.

Do not make Mature Green visually noisy enough to obscure enemies.

The difference should be readable at a glance but subordinate to combat readability.

# 24. HUD Changes

Do not add another large HUD element.

Use the existing territory bar.

## 24.1 Territory Composition

The bar should communicate:

```text
Green
Neutral
Rot
```

Neutral now has strategic meaning and should be visually legible.

Example situations:

```text
30% Green / 60% Neutral / 10% Rot
```

is relatively recoverable.

```text
30% Green / 10% Neutral / 60% Rot
```

is strategically dangerous.

These should not look equivalent.

## 24.2 Mature Green Within Green

Represent Mature Green as a darker or denser inner segment inside the Green portion.

Conceptual:

```text
Total Green:
████████████████████

Mature fraction:
█████████
```

The player should be able to read:

> I have reclaimed a lot of territory, but much of it is still fresh.

Avoid adding another percentage label unless testing shows that players cannot understand the graphic.

# 25. Territory Percentage Semantics

Global percentages remain informative but are no longer direct loss thresholds.

Recommended metrics:

```text
player_percent
neutral_percent
hostile_percent
mature_green_percent
mature_fraction_of_green
```

Definitions:

```text
mature_green_percent
    = map percentage that is both Green and above mature threshold

mature_fraction_of_green
    = mature Green area / total Green area
```

The second metric is especially useful for telemetry and balance.

# 26. Failure Condition

Do not add a fixed Rot-percentage defeat rule as part of this redesign.

The existing territory failure logic may remain temporarily while the new system is evaluated, but it should be reviewed separately.

The main new consequence of losing territory should come from:

- loss of mature movement routes;
- loss of Adaptation infrastructure;
- fresh territory fragility;
- hostile entrenchment;
- Canker spawn topology;
- spatial pressure.

If these consequences succeed, a new global territory defeat threshold may be unnecessary.

# 27. Adaptation Interaction Rules

The redesign must reinforce existing Adaptation identities rather than flatten them.

---

# 28. Spore

**Role after rework:** aggressive reclamation.

Spore should remain one of the strongest ways to convert successful combat into Green.

Rules:

- universal enemy death cleanse remains weak;
- Spore-specific Seeds may still create meaningful Green;
- Spore territory always starts Fresh unless explicitly upgraded;
- mass kills can therefore produce dramatic recolonization without instantly restoring mature infrastructure.

Desired fantasy:

> I killed the horde and rapidly reseeded the battlefield.

Not:

> Everything is fully restored because enemies died.

---

# 29. Bloom

**Role after rework:** frontline creation and temporary stabilization.

Bloom should excel at:

- creating Green;
- protecting newly reclaimed areas;
- buying time for Fresh Green to mature;
- interrupting Canker formation through local reclamation.

Existing protective mechanics such as Aftergrowth-style territory protection become more valuable because Fresh Green is intentionally fragile.

Avoid giving Bloom a universal maturity shortcut unless an upgrade or relic specifically supports that fantasy.

---

# 30. Fruit

**Role after rework:** mobile reclamation and route creation.

Fruit can create Green trails and remote patches that later become movement infrastructure.

This creates a satisfying long-term interaction:

```text
Fruit rolls through battlefield
→ leaves Fresh Green
→ player later uses route
→ route matures
→ becomes preferred movement lane
```

Fruit should be especially good at contesting distant Rot because of its spatial mobility.

---

# 31. Root

**Role after rework:** establishment, infrastructure, and recovery advantage.

Root should benefit strongly from the distinction between Fresh and Mature Green, but it must not become mandatory.

Root interactions may include:

- faster Green maturation;
- stronger or broader Root Network behavior on established soil;
- expanded Root Network reach;
- effects that depend on connected Mature Green;
- improved recovery of recently lost territory.

## 31.1 Existing Regrowth Conflict

The existing Regrowth mechanic uses lost-territory memory to regrow recently lost ground automatically and unopposed.

It restores control rather than maturity, so it does not completely erase sticky loss, but its current message is approximately:

> Losing this territory is temporary.

That conflicts with the rework's intended lesson:

> Reclaiming ownership is possible, but losing established territory has a lasting cost.

Regrowth should therefore be revised rather than simply deleted.

## 31.2 Preferred Regrowth Redesign: Recolonization Memory

Recommended behavior:

1. Root remembers recently lost player territory.
2. If that location remains Rot, memory alone does **not** freely overwrite hostile control.
3. Once the area becomes Neutral, remembered Root territory reclaims toward **Fresh Green** substantially faster than normal passive reclamation.
4. Restored territory begins at low maturity.
5. The memory expires after its normal or retuned duration.

Conceptually:

```text
Mature/Fresh Green
    -> lost to Rot
    -> Root remembers location
    -> player clears Rot to Neutral
    -> remembered soil recolonizes quickly
    -> Fresh Green
    -> must mature again
```

This preserves Root's fantasy:

> My garden knows how to come back.

without teaching:

> Enemy occupation does not matter because Root will undo it for free.

## 31.3 Fallback Alternative

If the preferred implementation is architecturally expensive, Regrowth may retain limited direct Rot reclamation only if:

- the rate is substantially slower;
- reclaimed territory always starts Fresh;
- it cannot instantly restore large lost regions;
- it does not bypass Canker pressure once Cankers are implemented.

The Neutral-first recolonization model is preferred.

# 32. Bramble

**Role after rework:** holding established ground.

Bramble should excel at:

- preventing Green loss;
- slowing hostile breakthrough;
- giving Fresh Green enough time to establish;
- protecting high-value mature lanes;
- defending regions during Canker warning windows.

The goal is not to make Bramble directly "generate maturity."

Its strength is helping territory survive long enough to mature naturally.

---

# 33. Thistle

Thistle already benefits from friendly ground and Root support.

This rework increases the strategic cost of abandoning Thistle-supported territory.

Expected interaction:

```text
Lose Green
→ lose support area
→ lose positional Thistle value
→ potentially allow Rot to entrench
```

Do not add additional Thistle punishment unless playtests show it is necessary.

The territory system itself should provide sufficient consequence.

---

# 34. Vine

**Role after rework:** combat clearing.

Vine should remain excellent at removing enemies.

It can:

- create safe windows;
- clear packs from contested ground;
- enable passive or authored reclamation.

It should not independently rebuild the garden unless relics or Evolutions explicitly add that capability.

A Vine-heavy build should feel:

> I can destroy the enemy, but I need time or another system to restore what they took.

This is a healthy build weakness.

---

# 35. Seedpod

Seedpod should behave similarly to other direct-damage Adaptations.

Its damage removes pressure.

It should not automatically gain strong territorial conversion simply because it kills many enemies.

Any territory interaction should come from explicit relics, Evolutions, or future authored mechanics.

---

# 36. Pruning Special Case

Pruning intentionally removes or harvests player territory.

This must **not** be interpreted as enemy territorial success.

The field should distinguish, directly or indirectly, between:

```text
territory lost to hostile corruption
```

and:

```text
territory intentionally removed by player Pruning
```

## 36.1 Required Protections

Player-authored Pruning should not:

- advance Canker timers by itself;
- create "scar" penalties intended for hostile loss;
- trigger enemy entrenchment simply because Green was harvested;
- be treated as a hostile breakthrough event.

If Pruning creates Neutral territory, Canker eligibility should still require actual Rot occupation.

This is likely enough to preserve its intended gameplay.

# 37. Performance Constraints

Territory systems already operate under significant simulation pressure.

This redesign must not add expensive full-field queries every frame.

## 37.1 Maturity Movement Lookup

Player movement requires only one local maturity sample per movement update.

This should be inexpensive.

The more important implementation requirement is that the territory movement factor composes with relic and other speed modifiers rather than fighting over a single setter.

## 37.2 Phase 2 Hot-Loop Budget

Phase 2 is the only early part of this redesign that adds meaningful work inside the TerritoryField per-cell simulation loop.

The field currently contains approximately:

```text
112 × 63 = 7,056 cells
```

at:

```text
simulation_hz = 30
```

which is approximately:

```text
211,680 cell steps / second
```

The loop is already performance-sensitive and hoists tuning values into locals such as:

```gdscript
step_diffusion_rate
step_sharpening_rate
...
```

The Rot-conversion implementation must follow the same style.

### 37.2.1 Do Not Use a Per-Cell Helper Call

The conceptual function shown elsewhere:

```gdscript
get_rot_conversion_factor(control)
```

is explanatory pseudocode only.

Do **not** implement the production hot loop as a GDScript function call for every cell.

At approximately 212k cell steps per second, avoidable GDScript call overhead is not free.

Compute the factor inline.

Conceptual shape:

```gdscript
var rot_conversion_factor := 0.0

if control < step_rot_release_control:
    if control <= -step_ownership_threshold:
        rot_conversion_factor = 1.0
    else:
        rot_conversion_factor = inverse_lerp(
            step_rot_release_control,
            -step_ownership_threshold,
            control
        )
```

Use the cheapest equivalent expression that preserves the intended fade.

### 37.2.2 Early-Out Non-Hostile Cells

The resistance factor is zero for Green and most Neutral cells.

Therefore the hot path should immediately skip the additional Phase 2 work when:

```gdscript
control >= step_rot_release_control
```

with the recommended prototype release point near:

```text
-0.10
```

Only genuinely hostile or near-hostile negative cells should pay for:

- the Rot factor fade;
- positive-direction sign checks;
- resisted advection;
- resisted diffusion;
- resisted sharpening;
- resisted natural spread.

Do not calculate four `lerpf()` resistance applications for every Green cell.

### 37.2.3 Hoist New Tuning Values

At the beginning of the step/batch function, hoist the new values into locals just like the existing simulation rates.

Recommended local naming:

```gdscript
var step_rot_release_control := tuning.rot_resistance_release_control
var step_rot_advection_multiplier := tuning.rot_conversion_advection_multiplier
var step_rot_diffusion_multiplier := tuning.rot_conversion_diffusion_multiplier
var step_rot_sharpening_multiplier := tuning.rot_conversion_sharpening_multiplier
var step_rot_spread_multiplier := tuning.rot_conversion_natural_spread_multiplier
var step_ownership_threshold := tuning.ownership_threshold
```

Do not repeatedly dereference tuning resources inside the inner cell loop.

### 37.2.4 Avoid Unconditional `lerpf()` Calls

The design pseudocode uses forms such as:

```gdscript
lerpf(1.0, multiplier, rot_conversion_factor)
```

for clarity.

Production code should avoid doing that unless:

```text
rot_conversion_factor > 0
AND
the relevant delta is moving in the positive conversion direction
```

For cells that are not eligible, preserve the existing arithmetic path.

Where the factor is exactly `1.0`, use the configured multiplier directly rather than interpolating.

### 37.2.5 Preserve Existing Fast Path

The most common case should remain close to the old loop:

```text
Green cell
or
Neutral cell above the negative release threshold
    -> no Rot-resistance calculations
    -> existing advection/diffusion/sharpening/spread path
```

The added cost should scale primarily with the amount of genuinely hostile territory on the field.

### 37.2.6 Required Performance Measurement

The project already exposes:

```text
TIMER_TERRITORY_BATCH
```

through the performance counters around the territory batch step.

Use that existing timer as the Phase 2 performance gate.

Record, at minimum:

```text
before Phase 2:
    median / p95 / p99 TIMER_TERRITORY_BATCH

after Phase 2:
    median / p95 / p99 TIMER_TERRITORY_BATCH
```

under identical deterministic fixtures.

Include at least:

1. mostly Green field;
2. mixed Green/Neutral field;
3. Rot-heavy field;
4. churning Green/Rot frontier;
5. a territory-heavy combat fixture at the established enemy cap.

The Rot-heavy case is especially important because it exercises the expensive branch most frequently.

### 37.2.7 Phase 2 Performance Exit Criterion

Phase 2 is not complete until the before/after `TIMER_TERRITORY_BATCH` result is recorded.

If the added logic causes a material regression:

1. verify the non-hostile early-out is actually taking effect;
2. verify tuning values are hoisted;
3. remove unnecessary helper calls;
4. remove unconditional interpolation;
5. profile the Rot-factor calculation itself;
6. only then consider simplifying the resistance curve.

Do not accept a significant hot-loop regression simply because the territory behavior is correct.


## 37.3 Canker Evaluation

Cankers are a later-phase feature and should not be implemented until the cheaper field changes have been profiled.

When they are added, do not repeatedly calculate local Rot percentage from raw pixels or cells for every possible point.

Use:

- coarse territory chunks;
- region summaries;
- low-frequency sampling;
- spatial caches;
- existing territory dirty-region updates.

Recommended evaluation frequency:

```text
2 to 4 evaluations per second
```

Canker behavior does not require frame-perfect precision.

## 37.4 Active Canker Cap

Initial hard cap:

```text
2 active Cankers
```

This is both a design and performance constraint.

## 37.5 Spawn Redirection

Canker spawn selection should reuse the existing spawn pipeline wherever possible.

Ideal architecture:

```text
existing wave spawn request
    ↓
spawn location policy
    ↓
edge location OR eligible Canker location
    ↓
existing enemy spawn function
```

Do not create a separate enemy-spawning subsystem for Cankers.

## 37.6 Territory-Source Telemetry Cost

Green-source instrumentation should aggregate counters rather than retain per-cell event history for the entire run.

Track enough information to answer:

```text
Which source reclaimed how much Neutral?
Which source reclaimed how much Rot?
How often did it trigger?
```

without generating large allocations or event logs in hot loops.

```gdscript
# Optional, only if required by architecture
```

Do not add large persistent per-cell source histories solely for telemetry.

# 40. Spawn Location Selection Pseudocode

```gdscript
func choose_spawn_location(request: SpawnRequest) -> Vector2:
    if not request.can_use_canker_spawn:
        return choose_perimeter_spawn(request)

    var eligible_knots := canker_director.get_eligible_knots_for_spawn(request)

    if eligible_knots.is_empty():
        return choose_perimeter_spawn(request)

    if randf() > get_total_canker_redirect_chance(eligible_knots):
        return choose_perimeter_spawn(request)

    var knot := choose_weighted_knot(eligible_knots)
    var location := find_safe_canker_spawn_location(knot, request)

    if location == INVALID_POSITION:
        return choose_perimeter_spawn(request)

    return location
```

Safety checks should include:

```text
distance from Grandma
collision validity
navigation validity
distance from protected spawn zones
enemy-specific restrictions
```

With two active regions and many enemies, repeated alarms could become exhausting.

# 44. Camera and Screen Feedback

Do not use strong full-screen effects for ordinary Canker formation.

Potential lightweight feedback:

- tiny localized camera impulse when a Knot activates;
- local screen-space marker if Knot is near the edge of view;
- subtle pulse from the affected ground.

The goal is to direct attention without pulling focus away from combat.

---

# 45. Off-Screen / Edge Awareness

Because Sporekeeper is single-screen, "off-screen" is not generally a concern, but combat clutter can still hide distant events.

During Canker warning:

- optionally show a small directional botanical marker at the HUD edge;
- marker should disappear when the warning is cancelled;
- do not use a persistent quest-arrow aesthetic.

The field itself should remain the primary communication method.

---

# 46. Tutorialization

Do not introduce the entire system through a large tutorial popup.

Teach through early-wave sequencing.

Suggested progression:

## Early Waves

Player starts on Mature Green.

They immediately notice movement is slightly better there.

## First Reclamation

New Green appears visually lighter.

No explanation required initially.

## First Meaningful Loss

Player loses part of the mature starting garden.

The visual difference makes the loss apparent.

## First Canker Warning

Show a short one-time tooltip:

> **Rot can take root if left uncontested. Reclaim the surrounding soil to stop it.**

After this, rely on visual language.

---

# 47. First Canker Timing

Do not allow Cankers during the first few tutorial waves unless the early campaign is explicitly designed around teaching them.

Recommended first prototype:

```text
canker_system_enabled_from_wave = 4 or 5
```

This should be tested against campaign pacing.

The player should first understand:

- Green;
- Rot;
- Fresh vs Mature;

before enemy infrastructure is introduced.

# 48. Difficulty Interaction

Do not immediately retune the campaign wave table when this system is added.

The redesign itself may significantly increase effective difficulty because:

- losing established Green matters;
- movement routes can disappear;
- interior enemy entry changes positioning;
- raw damage no longer fully restores the map.

Changing enemy HP, damage, density, spawn cadence, and territory strength simultaneously would make attribution impossible.

---

# 49. Balance Freeze During Initial Test

For the first comparison build, freeze:

- enemy HP scaling;
- enemy damage scaling;
- enemy movement scaling;
- wave spawn counts;
- enemy cap;
- territory attack strength;
- elite frequency;
- relic probabilities;
- upgrade offer rates.

Only modify territory consequence systems.

This allows a clean A/B comparison.

# 51. Tuning Philosophy

When testing, adjust systems in this order:

1. **Does Mature Green feel more valuable than Fresh Green?**
2. **Does the movement bonus cause the player to recognize established routes without becoming mandatory?**
3. **Does directional resistance to positive diffusion/sharpening make enemy-held ground meaningfully expensive to retake?**
4. **Which authored systems are actually responsible for large Rot -> Green recovery?**
5. **Can non-territory builds still recover through normal combat plus Neutral reclamation?**
6. **Does revised Root Regrowth preserve Root's identity without undoing hostile occupation?**
7. **Only after these are stable, do Cankers add useful spatial escalation?**
8. **Only then adjust numerical campaign difficulty.**

Do not tune several territory-generation sources downward at the same time as adding directional Rot-conversion resistance.

The asymmetry itself substantially increases the strategic value of any authored effect capable of converting Rot directly to Green.

# 52. Expected Player Behavior

The redesign is successful if players begin to make decisions like:

> "That eastern patch is Fresh. I can let it go."

> "The west has been Mature for several waves. I need to protect it."

> "I killed everything here, but the soil is still Neutral. I need to actually reclaim it."

> "That Rot patch has been sitting too long. I should deal with it before it roots."

> "I can keep fighting here, or I can cross the map to save my movement lane."

These are the target decision patterns.

---

# 53. Anti-Snowball Requirements

Every new mechanic must pass the following test:

> Does losing territory reduce the player's ability to recover territory?

If yes, reconsider it.

Approved examples:

- losing Mature Green removes a bonus;
- losing a Root-supported region removes that infrastructure;
- a Canker redirects existing enemies;
- lost Green must remature.

Dangerous examples:

- Rot slows Grandma below baseline;
- Rot increases total enemy spawns;
- Rot increases enemy damage;
- low Green reduces player damage;
- high Rot slows Green creation globally;
- Cankers multiply themselves uncontrollably.

The redesign should create pressure without creating a mathematical collapse spiral.

---

# 54. Canker Spawn Safety Rules

Canker redirects must be fair.

Minimum requirements:

- never spawn inside Grandma's immediate collision/safety radius;
- never spawn directly underneath a large active combat effect if that hides the telegraph;
- never spawn on invalid navigation or collision space;
- never create an enemy with no visible emergence tell;
- use existing spawn-delay / emergence rules where possible;
- do not bypass boss or elite introduction cinematics;
- do not redirect enemies whose attack pattern assumes perimeter entry.

---

# 55. Canker Candidate Fairness

Do not allow a Knot to establish:

- inside the starting Mature patch during its first instructional waves;
- immediately adjacent to Grandma;
- directly beneath critical HUD-overlap areas if the battlefield layout makes it unreadable;
- overlapping another Knot's influence region;
- from a tiny isolated Rot speck.

The local Rot-ratio requirement should naturally prevent the last case.

---

# 56. Interaction With Territory-Clearing Effects

After asymmetric spread is implemented, territory transitions should be treated as distinct verbs.

## 56.1 Canonical Transition Roles

```text
Neutral -> Green
    expansion / recolonization

Rot -> Neutral
    clearing hostile control

Rot -> Fresh Green
    direct reclamation

Fresh Green -> Mature Green
    establishment

Green -> protected Green
    defense / stabilization
```

These verbs should not automatically be valued as equivalent.

## 56.2 Canker Interaction

Once Cankers are implemented:

Any effect that converts:

```text
ROT -> NEUTRAL
```

should reduce Canker progress.

Any effect that converts:

```text
ROT -> GREEN
```

should also reduce Canker progress.

An effect that merely damages enemies should not reduce Canker progress unless it also changes field ownership.

## 56.3 Adaptation Audit Requirement

For each territory-producing Adaptation, relic, and Evolution, explicitly record which transitions it is allowed to perform.

This is especially important after passive `Green -> Rot` reclamation is disabled, because direct `Rot -> Green` effects become significantly more strategically valuable.

# 57. Interaction With Temporary Territory Protection

If an effect temporarily prevents territory loss:

- protected Green should continue maturing unless the effect explicitly says otherwise;
- Rot should not progress through protected cells;
- a Canker candidate whose local Rot falls below cancel threshold because of protection should cancel normally.

Do not create special Canker immunity rules for each Adaptation unless required.

The territory field should remain the shared source of truth.

---

# 58. Interaction With Territory Strength

If the existing field uses territory strength or resistance:

- Mature Green may continue to inherit any existing strength relationships;
- do not automatically add another large maturity-based resistance bonus unless already part of the design;
- the movement bonus alone is enough for the first test.

Avoid stacking several new Mature Green advantages at once.

Otherwise Mature territory could become too difficult to dislodge and the player may snowball.

---

# 59. Interaction With Relics

Existing territory relics should be audited under the new model.

Check for relics that:

- directly create Green on kill;
- restore huge Green areas;
- multiply Green creation;
- accelerate maturation;
- protect territory;
- depend on hostile percentage;
- trigger from territory loss.

For each relic, ask:

> Does this relic bypass the new reclaim → stabilize → mature loop?

If yes, determine whether that bypass is:

- an intentional rare power spike;
- too common;
- too efficient;
- strong enough to erase territorial consequence.

Do not broadly nerf relics until playtesting confirms a problem.

---

# 60. Interaction With Evolutions

Evolutions are allowed to bend the normal rules more dramatically.

Examples of acceptable Evolution-level effects:

- Green created by a specific Evolution starts partially Mature;
- reclaiming a Canker causes a large territorial burst;
- Mature Green propagates maturity to adjacent Fresh Green;
- a specific Adaptation can destroy Canker structures through a unique territory mechanic.

These should feel special precisely because baseline systems do not do them.

---

# 61. Save / Replay / Determinism

If the game supports deterministic test fixtures or replayable seeds:

Canker logic should use the same seeded random source as the rest of combat.

Do not use an unseeded global random call for:

- Knot selection;
- redirected spawn decision;
- redirected spawn offset.

This keeps performance and balance fixtures reproducible.


Ownership should recover substantially faster than maturity.

That gap is core to the system.

# 65. Success Criteria

The first prototype is successful if most of the following become true:

1. Players visibly react to threatened regions before reaching near-total territory loss.
2. Losing established territory feels more consequential than losing newly created territory.
3. Killing a horde no longer automatically makes the map feel fully repaired.
4. Territory-focused Adaptations provide strategic value that raw DPS cannot fully replace.
5. Non-territory builds remain viable through Neutral-clearing and slow passive recovery.
6. Cankers cause repositioning without increasing total enemy population.
7. Players understand why Cankers appeared.
8. Players understand how to remove Cankers without reading a detailed tooltip.
9. The game does not create frequent unrecoverable death spirals.
10. Performance remains inside the established frame-time targets.

---

# 66. Failure Signals

Revisit the design if:

- players ignore Mature Green because the movement bonus is imperceptible;
- players feel forced to choose Root;
- Cankers repeatedly spawn enemies in unfair positions;
- players cannot recover territory without Spore/Bloom/Fruit;
- Fresh Green dies so quickly that reclamation feels pointless;
- Mature Green is so durable that late-game territory becomes permanently solved;
- Cankers form constantly during normal oscillation;
- players spend the entire wave chasing Canker warnings;
- damage builds become nonviable;
- total CPU cost increases materially because local territory ratios are queried too frequently.

---

# 67. Recommended Implementation Order

The codebase audit changes the original rollout substantially.

Cankers should no longer be treated as the early fix.

The first priority is to make the existing field consequential using the cheapest and most foundational changes already supported by the architecture.

---

## Phase 1: Make Old Green Valuable

Implement:

- the existing control-derived starting Green maturity ramp is replaced with a flat `STARTING_GREEN_MATURITY = 1.0` assignment;
- newly claimed Green continues to start Fresh;
- movement speed is refactored into composed factors;
- Mature Green provides the territory movement bonus;
- Fresh and Mature Green become visually distinguishable;
- the existing territory HUD subtly represents Mature Green within total Green.

Do not change authored territory-generation numbers yet.

### Codebase focus

- modify the existing inline `reset_field()` maturity write so every starting player-owned Green cell receives the flat starting maturity value rather than the current control-derived ramp;
- refactor the single speed-multiplier slot before adding per-frame territory speed;
- verify relic speed modifiers still behave identically after composition.

### Primary test question

> Do I care more when old territory is destroyed than when Fresh Green is lost?

### Exit criteria

Proceed only if:

- the player can feel the mature movement advantage;
- the bonus is noticeable but not mandatory;
- losing Mature Green has a clear visual and mechanical consequence;
- no relic movement behavior is overwritten.

---

## Phase 2: Make Rot Genuinely Different From Neutral

Implement **directional Rot-conversion resistance across all four control-changing channels**:

1. pressure advection;
2. diffusion;
3. sharpening;
4. natural spread.

### Canonical Gate

Classify whether the cell is established Rot from:

```text
pre-advection control
```

not from:

```text
transported
```

Generic positive pressure advection must respect the same resistance.

Explicit authored territory stamps may bypass it when their design says they should.

### Required behavior

For a cell that was confidently Rot before advection:

- damp positive pressure-advection delta;
- damp positive diffusion;
- gate/damp positive sharpening;
- suppress/damp positive natural spread;
- fade resistance through a small negative-control release band.

For Green being attacked by hostile pressure:

- leave existing behavior unchanged except for preexisting mechanics such as maturity resistance.

Neutral-band cells remain easy to claim.

Do **not** add a generic enemy-death cleanse.

### Codebase focus

Phase 2 belongs inside the per-cell simulation step.

The implementation must explicitly preserve:

```text
control_before_advection
transported_after_advection
```

because those values answer different questions.

### Primary test question

> Does established Rot resist generic positive advection/diffusion/sharpening while Rot's ability to attack Green remains effectively unchanged?

### Exit criteria

Proceed only if:

- meaningful Rot patches are substantially harder to erase passively than Neutral soil;
- generic pressure cannot silently bypass the resistance;
- Bloom-style pressure only gets special Rot-reclamation power from explicit authored territory effects;
- Neutral remains naturally recoverable;
- the resistance does not symmetrically harden Green;
- boundary behavior is stable through the release band;
- non-territory builds retain the intended recovery floor;
- the field does not become permanently locked after one setback;
- before/after `TIMER_TERRITORY_BATCH` median, p95, and p99 are recorded on identical fixtures;
- Phase 2 does not introduce an unacceptable territory-batch regression.
---

## Phase 3: Instrument Territory Sources

Before changing territory-generation balance, measure it.

Implement source-attributed counters for:

```text
trigger count
Neutral -> Green
Rot -> Green
optional maturity created
```

At minimum identify output from:

- Spore;
- Bloom;
- Fruit;
- Root;
- relics;
- Evolutions;
- passive spread;
- other meaningful territory sources.

### Primary test question

> Which systems are actually causing horde kills to refill the battlefield?

### Required output

After a representative run, it should be possible to answer questions such as:

```text
What percentage of direct Rot reclamation came from Spore?
How much Green came from passive Neutral spread?
Which relic created the largest Rot -> Green swing?
How often did a kill-reactive effect trigger?
```

### Exit criteria

Do not begin broad Adaptation tuning until the major territory sources are attributable.

---

## Phase 4: Audit Adaptation Reclamation Roles

Use Phase 3 telemetry to decide explicitly which systems specialize in each territorial verb:

```text
Neutral -> Green
Rot -> Neutral
Rot -> Fresh Green
Fresh -> Mature
prevent Green -> Rot
```

Do not assume every territory Adaptation should directly perform `Rot -> Green`.

Potential role direction:

```text
Spore:
    strong aggressive reclamation

Bloom:
    localized contested reclamation and stabilization

Fruit:
    mobile expansion / route creation, potentially weaker against entrenched Rot

Root:
    establishment and recovery advantage rather than fastest direct reclamation

Bramble:
    preservation and stabilization
```

These are role guidelines, not automatic balance changes.

### Primary test question

> Does raw damage still replace territory specialization, or do different Adaptations now solve different territorial problems?

### Important tuning rule

Making established Rot resist positive diffusion and sharpening already increases the value of authored effects that can directly push hostile control toward Green.

Do not automatically nerf those effects before measuring them under the new field rules.

---

## Phase 5: Redesign Root Regrowth

Replace the current "lost territory automatically comes back" lesson with:

> Recently lost Root territory is easier to recolonize after hostile control has been cleared.

Preferred implementation:

```text
Green lost to Rot
    -> Root remembers location
    -> location remains Rot: no free restoration
    -> Rot becomes Neutral
    -> memory accelerates Neutral -> Fresh Green
    -> territory must mature again
```

### Primary test question

> Does Root still feel unusually good at recovering from territorial loss without making enemy occupation temporary or meaningless?

### Exit criteria

- Root preserves a distinctive recovery identity;
- Regrowth does not freely bypass active Rot;
- restored territory does not recover previous maturity;
- Root is helpful but not mandatory.

---

## Phase 6: Add Cankers as Escalation

Only after Phases 1 through 5 are proven should persistent local Rot gain enemy infrastructure.

Implement:

- local Rot sampling;
- Canker candidate persistence;
- warning state;
- Canker visual telegraph;
- active Canker creation;
- safe spawn redirection;
- reclamation-based destruction;
- reestablishment cooldown;
- hard active-Canker cap.

Cankers redirect existing spawn budget.

They do **not** increase total enemy population.

### Primary test question

> Does territory that remains ignored for a long time create interesting positional pressure beyond the normal cost of losing Green?

### Canker role

Cankers should escalate neglect.

They should not be required to make the basic territory system matter.

If Phases 1 through 5 already produce strong territorial decision-making, Cankers can be introduced conservatively.

---

## After Phase 6: Campaign Retuning

Only after the territory loop is stable:

- reevaluate enemy density;
- reevaluate territory damage;
- reevaluate early/mid campaign pressure;
- reevaluate wave scaling;
- reevaluate elite timing;
- reevaluate Canker activation timing.

Do not assume the pre-rework wave table still needs the same difficulty increases.

# 70. Unit and Simulation Tests

At minimum verify:

## Green Maturity

- starting Green uses the revised seeded Mature value;
- new Green initializes at expected Fresh value;
- Green maturity rises at correct rate;
- ownership loss removes or decays maturity correctly;
- reclaiming does not restore old maturity.

## Movement Composition

- local territory sampling uses multiple nearby samples rather than one nearest cell;
- Neutral / Rot / unstable-boundary local averages return `1.0`;
- Fresh Green is approximately `1.0`;
- Mature Green reaches configured maximum;
- movement-side ownership hysteresis prevents flicker at the positive ownership boundary;
- maturity interpolation is monotonic;
- relic speed multiplier remains intact while territory multiplier changes;
- changing territory does not overwrite unrelated movement modifiers.

## Directional Rot Conversion

- the Rot gate is derived from `control` before advection, not `transported`;
- a confidently Rot cell cannot evade resistance solely because pressure advection moved `transported` near Neutral;
- positive pressure-advection delta is damped while Rot-conversion resistance applies;
- positive diffusion is damped while Rot-conversion resistance applies;
- positive sharpening is gated/damped while Rot-conversion resistance applies;
- positive natural spread is suppressed/damped while Rot-conversion resistance applies;
- negative advection/diffusion pressure from Rot into Green is not symmetrically damped;
- resistance fades cleanly through the configured release band;
- cells near the ownership threshold do not rapidly toggle behavior;
- explicit authored territory stamps still behave according to their own rules;
- a generic pressure-only relic does not gain an unintended direct Rot-reclamation bonus.

## Territory Source Telemetry

- source trigger count increments correctly;
- Neutral -> Green and Rot -> Green are attributed separately;
- passive spread is not mislabeled as an Adaptation source;
- source telemetry does not double-count overlapping stamps.

## Root Regrowth

- recently lost Root territory is remembered;
- memory alone does not freely overwrite active Rot in the preferred implementation;
- remembered Neutral soil recolonizes faster than normal;
- recovered territory starts Fresh;
- expired memory no longer accelerates reclamation.

## Canker, Phase 6

- candidate does not form below activation ratio;
- candidate progresses above activation ratio;
- candidate cancels below cancel ratio;
- warning transitions correctly;
- Canker respects global cap;
- Canker cannot immediately re-form during cooldown;
- reclaiming surrounding Rot destroys the Canker;
- damage alone does not destroy the Canker.

## Spawns, Phase 6

- total spawn budget is unchanged;
- redirected spawn falls back safely;
- bosses/elites remain restricted;
- player safety distance is always respected.

# 75. Final Intended Gameplay Loop

The target territory loop is:

```text

    ↓
Player expands into Neutral soil
    ↓
New Green begins Fresh
    ↓
Fresh Green survives
    ↓
Green matures
    ↓
Mature ground becomes movement and Adaptation infrastructure
    ↓
Enemies corrupt Green into Rot
    ↓
Lost Mature territory loses its accumulated investment
    ↓
Player wins the immediate combat
    ↓
Raw damage alone does not automatically repaint the battlefield
    ↓
Authored territory systems clear or reclaim Rot
    ↓
Neutral soil becomes available for passive Green recolonization
    ↓
Reclaimed Green begins Fresh again
    ↓
Player chooses whether to stabilize and remature it
    ↓
Root can accelerate recovery of remembered soil after hostile control is cleared
    ↓
If Rot remains ignored for a long time in the later system:
        Canker begins forming
    ↓
Player either contests the region
or
allows hostile infrastructure to establish
    ↓
Canker redirects part of the existing enemy spawn budget inward
    ↓
Player retakes surrounding soil
    ↓
Canker withers
    ↓
Recovered territory still rebuilds from Fresh state
```

The loop should continuously produce spatial decisions without adding another active ability, currency, or menu.

Most importantly, Cankers are the **final escalation layer**, not the thing making the earlier territory states meaningful.

# 76. Final Design Summary

The revised implementation should make territory consequential through **investment, reclamation friction, and eventually enemy use of neglected space**, not through global percentage punishment.

The canonical rules are now:

1. **Starting Green is small but fully Mature.**
2. **All ordinary newly claimed Green starts Fresh.**
3. **Movement-speed modifiers are composed rather than written through one shared global slot.**
4. **Mature Green provides a modest movement advantage.**
5. **Losing Mature Green destroys investment that takes time to rebuild.**
6. **The continuous field applies directional resistance across pressure advection, diffusion, sharpening, and natural spread when positive pressure tries to convert established Rot, while Rot pressure into Green remains unchanged.**
7. **No universal enemy-death cleanse is added in the first implementation.**
8. **Existing authored kill-to-territory effects are measured before they are retuned.**
9. **Neutral -> Green and Rot -> Green output are tracked separately.**
10. **Adaptations are audited around distinct verbs: expansion, clearing, direct reclamation, establishment, and defense.**
11. **Root Regrowth becomes a recovery advantage rather than a free undo of hostile occupation.**
12. **Cankers are added only after the cheaper field changes prove insufficient or need further escalation.**
13. **Cankers redirect existing enemy spawns instead of increasing enemy count.**
14. **Cankers are removed by reclaiming territory, not by dealing damage.**
15. **No global Rot threshold, enemy stat multiplier, Green damage multiplier, or Rot movement penalty is required.**
16. **Campaign balance remains frozen until the territory rework is isolated and tested.**

The intended behavioral outcome remains simple:

> The player should look across the battlefield, recognize that one specific area is becoming strategically costly to lose, and deliberately change where they are fighting.

The new implementation order is designed to discover the minimum amount of machinery required to create that behavior.

If maturity value, asymmetric reclamation, and better-authored territory outputs are already enough, Cankers should remain a restrained escalation mechanic rather than becoming a dependency of the entire territory system.
